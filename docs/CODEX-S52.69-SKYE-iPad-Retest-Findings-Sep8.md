**Status:** Five real bugs found and fixed, deployed/committed. A live, tab-by-tab QA pass on the real iPad mini Simulator surfaced a further, larger backlog — captured here so it isn't lost in chat scrollback.

**2026-09-09 addendum — second Simulator QA pass, after S52.71 steps 1-3 shipped (crew-role onboarding/RoleSwitcher, Pilot's "My Aircraft(s)" panel, type-rating field).** Confirmed working in this pass: the Pilots/MX/Dispatch persona switcher, and the new "My Aircraft(s)" tab is present in both Pilot and MX tab lists. Everything below is a fresh finding from this pass, distinct from the items above unless noted:

1. **Map tab doesn't render in portrait — needs landscape. FIXED, not yet device-verified.** Root cause: `AviationMap.jsx`'s Leaflet `MapContainer` measures its container box once at mount and never re-measures on its own (no `ResizeObserver`/`invalidateSize()` anywhere in the file) — every link in the height chain (block `height: 560` → `AviationMap`'s explicit pixel height → wrapper divs → `.main`) is a real, non-zero value in both orientations, so this wasn't a CSS/layout bug at all. If the map mounts before the single-pane portrait layout settles (or briefly behind the chat overlay), Leaflet bakes in a 0-sized tile grid that only recovers when a real `resize` event fires — exactly what rotating to landscape does. Fix: added `MapResizeFix` (a small internal helper next to the existing `RecenterMap`) that runs a `ResizeObserver` on the map's actual container element and calls `map.invalidateSize()` on any size change — covers orientation change, layout-settling races, and tab-switch-back-to-Map. Sanity-checked in Chrome at a simulated 744×1133 portrait viewport (real tiles loaded, non-zero container), but the original bug needed a real device rotation to reproduce, so **still needs a real Simulator/device retest** before calling it fully closed.
2. **Tab bar overflows the viewport on both Pilot and MX. FIXED, and turned out to be the SAME root cause as item 1 above.** Two layers: (a) the tab row itself had no `overflow-x`/`flexShrink` handling at all (`AviationWorkerCanvas.jsx`'s tab-bar `<div>`) — fixed, now horizontally scrollable. (b) The real root cause, found while verifying (a): `.appShell` (`App.css` line 74) is `display:flex` with **no `flex-direction` override at mobile width** — only `.dualPanel`'s was set to `column` (line 972). With `.appShell` still a flex row, `.topbar` (a visible sibling of `.dualPanel`, `width:100%`) sat *beside* `.dualPanel` instead of stacked above it, and `.topbar`'s real width squeezed `.dualPanel` — and everything inside it, the whole canvas including the tab bar — to a measured **0×33px positioned entirely past the right edge of the viewport** at 744px (iPad-mini portrait). This is the actual mechanism behind "tabs running off the page" — the tabs/canvas weren't overflowing their own container, their container had zero width. **This is also very likely the real root cause of item 1's portrait Map bug** (the map's container would measure 0-width at the same broken layout state) — item 1's `ResizeObserver`/`invalidateSize()` fix is still worth keeping regardless (it's Leaflet's own correct fix for the general "container resized after mount" class of bug), but this `.appShell` fix may be what actually closes item 1 for real. Fixed with one line: `.appShell{ flex-direction:column; }` added inside the same `@media (max-width:1023px)` block. Verified live at 744px: `.dualPanel`/`.main` now measure a real 744px wide, tab bar correctly scrollable (`scrollWidth` 1280 > visible width), map loading real tiles. Not yet device-verified.
3. **Map's default base layer should be satellite, not the current default. FIXED.** `AviationMap.jsx`'s `satelliteOn` state defaulted to `false`; changed to `true`. One line.
4. **Scratch Pad doesn't persist drawings. FIXED — real bug found, not a missing feature.** `DrawingCanvas.jsx`'s `finishStroke()` nulled out `currentStrokeRef.current` *synchronously* right after calling `setStrokes(prev => [...prev, currentStrokeRef.current])` — but React's updater function reads that ref lazily when it actually invokes it (not at call time), so by then the ref was already `null`. Every completed stroke was silently recorded as `null` in state — skipped by `redraw()` (so nothing ever reappeared) and faithfully persisted to localStorage as `[null]` (so the save mechanism itself was never broken, it just never had real data to save). Fixed by capturing the completed stroke into a local variable before nulling the ref. Verified live: drew a stroke, confirmed real `{color, points}` data (not `[null]`) written to `localStorage`, reloaded the page fresh, confirmed the stroke redraws and Undo is enabled — persistence genuinely works now.
5. **Copy bug: empty-state prose says "tell Alex" instead of "tell Skye." FIXED.** 28 user-facing string literals across `aviationCanvasData.js` (17) and `AviationWorkerCanvas.jsx`'s `*ToBlocks` functions (11) referenced the generic default-worker name instead of the active Skye persona. Deliberately left untouched: `aviationCanvasData.js:1096` (`"Rivera, Alex"` — a crew member's actual name in fixture data, not the persona), and code comments in both files (historical references to old UI text, not user-visible). Verified: no other "Alex" references remain except those two categories.
6. **NOTAMs render raw JSON instead of parsed text. FIXED.** Confirmed root cause: the real Notamify response shape (`services/aviation/notams.js`'s `normalizeNotam()`) is `{ number, icao, summary, category, raw, startsAt, endsAt }`, but `AviationWorkerCanvas.jsx`'s `"notams"` fetch branch was reading `.text`/`.message`/`.notamId`/`.id`/`.airport`/`.location` — none of which exist on the real object — so every card fell through to a `JSON.stringify(n)` fallback. Remapped to the real field names. Verified live on Dispatch's NOTAMs tab: real, readable cards (e.g. `PHOG` / `01/339` / "Taxiway F closed to aircraft with wingspan over 118 ft."), no JSON text.
7. **Chat reliability — a response sometimes "thinks then stops"** with no completion. New finding, main Skye chat (not the separate EFB-internal-chat redundancy question already captured above).
8. **Tab-switch renders a brief flash of chat before landing on an add-item form.** New finding, a rendering-order glitch.
9. **Feature ask: Release Flight should be a two-step build-then-release. DONE.** `ReleaseFlightModal` now has a `step` state gating two distinct screens: "Build a flight package" (all the existing field entry, weather/W&B ack, `WeightBalanceCalculator`/`PerformanceCalculator` — unchanged, just gated behind `step === "build"`) then "Review & release" (a new read-only package summary + the existing verification/re-affirmation/status/crew-notify UI, unchanged otherwise, + the actual release button). Wiring Terrain Profile to "the active route" requires that real flight-plan state to exist first, which is the same already-tracked, highest-priority rebuild item from earlier in this doc (a real structured flight-planning tool), not a small follow-on. Did not fake a connection to the fixture data to appear done — flagging the dependency instead.
11. **Feature ask: an easy light/dark mode switch for Skye, with a real per-context default. DONE.** Added a new CSS custom-property theme system scoped to `[data-av-theme]` (`App.css`), so toggling never touches the rest of the app — only the aviation canvas's chrome (backgrounds/text/borders) inverts. Deliberately left unchanged in both themes: status/safety colors (No-Go/Caution/Advisory/Reference/Go bands) and the brand-blue action-button gradient — these are semantic signals, not decoration, and read fine in both themes as-is. Default is worker-aware (Pilot → dark, MX/Dispatch → light, matching Sean's framing) but a manual toggle (persisted per-device in localStorage) always wins once explicitly chosen. Converted ~194 lines across `AviationWorkerCanvas.jsx`'s chrome-neutral hex literals (text/border/subtle-background colors) to the new tokens — a mechanical but carefully property-scoped pass (text vs. background vs. border matched separately) to avoid inverting the wrong thing; one intentional exception preserved (a fixed dark table-header background that's supposed to stay dark regardless of theme). Verified live in both themes with screenshots — real contrast, no invisible text, toggle button itself is theme-aware. **Scope note:** this pass covers the main canvas (`AviationWorkerCanvas.jsx`) only — `AviationMap.jsx`'s own chrome, `CoPilotEFB.jsx`, and a few smaller modal-adjacent files weren't touched in this pass.

## Role-based onboarding + home screens (Sean's spec, live — the big one)

This is a coherent product direction spanning most of tonight's smaller findings, not an isolated fix. Captured close to verbatim.

**General mobile-environment principle:** the canvas should be the initial/primary view on mobile/tablet, with the Skye chat button always at-the-ready (floating) — not chat-first. This confirms and extends work already in place (aviation canvas-first at mobile tier, shipped 2026-08-30).

**RH nav menu should default collapsed**, not open. (Not yet matched to a specific component in code — verify against the actual right-panel/nav toggle before implementing; several small header icons were seen tonight that could be this.)

**First-run role selection, professionally worded:** on first major usage, ask "are you a pilot, maintenance tech, or dispatch" (his phrasing note: use professional wording, not internal shorthand like "MX"). That choice drives the entire opening experience from then on — with easy switching afterward for the shared-device case (one company iPad passed between a pilot, a mechanic, and a dispatcher).

**Pilot opening screen:** the Map — your location, radar, weather — with **New Flight** and other nav functions immediately accessible from there. (Ties directly to the already-flagged "Log Flight exists, Plan/New Flight doesn't" gap — this spec answers where that action should live.)

**MX (Maintenance Tech) opening screen:** Fleet Status + your assigned aircraft's daily/weekly/monthly checklist and notes. Sean's specific vision: a **half-report, half-chat** hybrid screen — Skye greets by name and summarizes what's on the plate today and this week ("Hi [name], here's what's on your plate for today and this week. How can I help?"), then quick access to a fleet status manifest and a map showing asset locations. This is essentially the Duty-tab reference-design idea (rolling summary + gauges/status) fused with a personalized conversational opener, applied as the actual home screen for this role.

**Dispatch opening screen:** same pattern as MX — a daily/weekly briefing + conversational "how can I help" opener, plus quick access to a map showing asset locations.
