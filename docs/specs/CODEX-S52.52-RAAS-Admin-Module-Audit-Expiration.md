# CODEX S52.52 — RAAS Admin Module: Content Management, Audit Trail, Expiration (Scope Only — Not Yet Built)

**Status:** SCOPED (2026-08-16), not built. Written up at Sean's request after he asked how Studio Locker documents actually get updated, mid-DPP-demo with Elise.
**Author:** Sean Lee Combs + Claude Code
**Predecessor:** CODEX-S52.48 (established `constraintRaasModules` as the canonical admin-rules system), S52.49 (rolled RAAS content out to 4 more workers, all still script/API-authored), S52.50 (DPP report pipeline — surfaced the same "no admin path" gap for a different vertical).

---

## Why this exists

Studio Locker's "Worker Libraries" panel is labeled **READ-ONLY** in the product today, and that label is accurate in a way that's actually a problem: there is no admin path anywhere in either app to create or edit a `constraintRaasModules` document. The backend has a complete CRUD API (`/v1/admin:raas:module:create/update/transition/counsel/section:add/update/remove/list/get/compose`, all in `functions/functions/services/raas/constraintModules.js` + routes in `index.js` ~16663-16800), but zero frontend surface calls any of it — **confirmed via `grep -rln "admin:raas:module\|admin/raas/module" apps/business/src apps/admin/src --include="*.jsx" --include="*.js"`, zero matches in either app**, not an assumption. Today the only way to add rules content is what happened for Max's GAAP module: a one-off Node script, run by hand, by an engineer.

That doesn't scale. S52.49 rolled the *query-tool* pattern out to Contacts/Marketing/IR (HR excluded there, correctly, since it has no data store to query) — but the *RAAS-content thinness* problem this spec exists to fix applies to all four non-accounting workers, including HR: Contacts 625 / Marketing 715 / IR 853 / HR 2k chars, all thin placeholder docs per S52.49. There's no way for a non-engineer — Sean, or a domain expert like Elise for DPP — to actually author real content for any of them. This spec fixes the access path, not the content itself.

## What already exists to build on

- **Full CRUD service layer** (`constraintModules.js`): `createModule`, `updateModule`, `addSection`, `updateSection`, `removeSection`, `transition`, `markCounselReviewed`, `composePromptText` (live preview), `listModules`, `getModule`. Nothing here needs rebuilding — the admin UI is a client for what's already there.
- **A real state machine, verified against the actual `ALLOWED_TRANSITIONS` constant** (not assumed from the prose description): `draft → {review, deprecated}`, `review → {draft, live, deprecated}`, `live → {deprecated}` only, `deprecated → {draft}`. There is **no direct `live → draft` transition** — editing a live module is a genuine two-hop path (`live → deprecated`, then `deprecated → draft`), both of which already exist as callable functions. The admin UI can walk an admin through both hops using only existing backend calls, so "no new backend logic needed" still holds — but the UI needs to model this correctly as two explicit steps (with the deprecation implication visible to the admin), not casually described as "drop back to draft."
- **A counsel-review gate**: `counsel_review: {required, reviewer, reviewedAt, approval_notes}` — a module cannot go live without it. This is chain-of-command at the whole-module level already.
- **A half-wired staleness hook**: every module has `notice_window_days` (defaults to 7) and `last_propagated_at` — fields clearly intended for an expiration/review-reminder mechanism that was never finished. Nothing reads or enforces these today.
- **Per-section `source_refs`** — a place to cite where a rule came from (a regulation, a URL, an internal SOP), already in the schema, currently just an unstructured array.

## What's missing — real gaps

- **No UI at all.** Not "needs polish" — genuinely zero frontend code calls the admin routes.
- **No audit history.** Mutations only carry `updatedBy`/`updatedAt` on the module doc itself — last-write-wins, no record of what changed or from what. This is inconsistent with the platform's own core invariant (CLAUDE.md: "Records are never overwritten; state is computed from event history") — every other canonical collection in this system is append-only, and this one currently isn't.
- **No per-section expiration.** `notice_window_days` is module-level and unenforced. A section sourced from an external regulation that changes and a section sourced from timeless internal SOP shouldn't share one staleness clock — and right now neither has one that does anything.
- **Deprecating a module does not actually take it offline for real chat traffic — found while writing this spec, not previously known.** `workerPromptComposer.js` (what real chat requests call) filters `constraintRaasSources` only on `load_when`, never on the referenced module's status, then calls `composePromptText` unconditionally. `composePromptText` itself only `console.warn`s on a non-live module — it does not refuse to compose. So the two-hop edit path (`live → deprecated → draft`) does not stop a module from being served mid-edit the way "deprecated" implies; only `addSection`/`updateSection`/`removeSection`'s own guard (which does correctly refuse to write to a live module) protects anything, and that's a write-path guard, not a serving-path guard.
  **This is not a one-line fix — the naive fix creates a worse problem, caught in review.** Making the composer skip any non-`live` module closes the "still serving" bug but replaces it with a content *blackout*: since editing a live module requires the two-hop `live → deprecated → draft` path, and there is no versioning (draft and live are the same document, not separate versions), the moment an admin starts editing accounting's GAAP module, real chat traffic loses the no-fabricated-figures rule entirely for the whole edit-review-republish cycle — not just at the instant of publish. That's a materially worse failure mode than the dormant bug it fixes. The real fix needs to decouple *what's being edited* from *what's being served* — see §1a for the proposed shape. This is a named design decision for sign-off, not a small backend fix bundled into the UI spec.
- **No distinct approval step for web-link sources.** `markCounselReviewed` is the same action whether the reviewer wrote the rule themselves or is approving a rule derived from a URL they may not have actually opened. Approving a web-link-sourced rule should require confirming the *fetched content*, not just clicking approve on the reviewer's own recollection of what the page said.

## Proposed shape (for review, not yet built)

### 1. Admin UI — `apps/admin`, new page (e.g. `RaasModuleAdmin.jsx`)
- List view: all modules, status, domain, section_count, last_propagated_at, notice_window_days, a "needs review" flag (see #3).
- Create module form: moduleId, name, description, domain, jurisdiction_scope, disposition_default.
- Edit view: add/edit/remove sections — title, body_markdown, priority, section_type, disposition_override, source_refs (plain citation text or a URL). To edit a *live* module, the UI walks the admin through the real two-hop path (transition to `deprecated`, then to `draft`) rather than implying a single "unlock for editing" action. **The backend write-guard only checks `status === 'live'`** (verified directly in `addSection`/`updateSection`/`removeSection`) — a module in `review` is *not* blocked from being edited at the data layer. "Draft state only" as a UI policy is therefore enforcing something the backend doesn't; either the UI must independently disable edit controls whenever status is `review` (not just `live`), or — more consistent with how this state machine defends itself everywhere else — the backend guard should be hardened to also refuse writes to a `review`-status module, so a module mid-review can't be edited out from under the reviewer by relying on UI discipline alone.
- Live preview of the composed prompt text before publishing, using the already-existing `/v1/admin:raas:module:compose` route — so an admin sees exactly what a worker will receive, not just the raw sections.
- Counsel-review action: reviewer name + approval notes, gated the same way `markCounselReviewed` already requires.
- Transition buttons respecting `ALLOWED_TRANSITIONS` as-is.

### 1a. Fix `workerPromptComposer.js` without introducing a content blackout during edits — a real design decision, not a small backend fix
The naive fix (skip any source whose module isn't `status === "live"`) is wrong on its own: it would take a live module fully dark to production chat traffic for the entire duration of every edit, since this system has no versioning — draft and live are the same document. **Proposed shape**: add a `liveSnapshot` field on the module doc (composed sections + composed text + `publishedAt`), written whenever a module transitions *to* `live`. `workerPromptComposer.js`/`composePromptText` serve from `liveSnapshot` unconditionally — regardless of whatever authoring status the document is currently in — so a module being edited (`deprecated` → `draft` → `review`) keeps serving its last-published content the whole time, and `liveSnapshot` is only overwritten when the edited version actually reaches `live` again. A module that has never been live (first-time authoring) has no `liveSnapshot` and correctly serves nothing. This is additive (one new field, one new write on the existing live-transition path, one read-path change in the composer) rather than a full versioning rewrite, but it's still new design, not a one-line skip — flagged for sign-off below, not assumed.

### 2. Audit history — new `constraintRaasModules/{id}/history/{entryId}` subcollection
- Append-only, one entry per mutation: action type, actor uid, full before/after doc snapshot, timestamp. **Correcting an overclaim in an earlier draft of this doc**: this is *not* actually the same shape as the Vault's own append-only pattern — the Logbook (CLAUDE.md: "each DTC owns a Logbook of immutable events") logs discrete *events* (registration, lien added, transfer), not full-document snapshots per change. Full-snapshot-per-mutation is a deliberate divergence, justified on its own merits (simpler to build, and "what did this module look like before/after this edit" is more directly useful for a content-review rollback than reconstructing state from a stream of field-level diffs) — not because it matches an existing pattern, because it doesn't.
- Every existing service function (`createModule`, `updateModule`, `addSection`, `updateSection`, `removeSection`, `transition`, `markCounselReviewed`) gets a matching history-write, in the same transaction where the existing code already uses one.
- This is additive to the existing functions, not a rewrite — same call sites, one more write each. **Caveat**: only `createModule` (and by extension `transition`/`markCounselReviewed`, since accounting's module reached `live`) has been exercised anywhere in this CODEX chain. `addSection`, `updateSection`, `removeSection`, and `composePromptText`'s preview mode haven't been called by anything built so far — "nothing needs rebuilding" is a claim based on reading the service file, not on having run these paths. Worth a quick smoke test of the untested functions before scaffolding the admin UI on top of them.

### 3. Expiration / staleness
- Add optional `review_by` (date) per-section, independent of the module-level `notice_window_days`.
- New scheduled function `raasContentStalenessCheck` (daily cron, same pattern as `regulatoryIngestDaily`/`checkTrialExpiry` already in this codebase): scans live modules for sections past `review_by`, sets a `needsReview: true` flag surfaced in the admin list view. This part needs no external fetches — it's a date comparison.
- For web-link-sourced sections: store a content snapshot/hash **once, at the same review-time moment §4 already requires the reviewer to view the fetched content** — one fetch serves both the "show the reviewer what they're approving" need and the staleness baseline, not two separate fetch events. Comparing against that stored baseline later (to detect drift) is a genuinely separate, currently-unspecified mechanism: does `raasContentStalenessCheck` refetch every URL in every live module's `source_refs` daily? That has real implications — rate limits on regulatory sites, latency, and failure handling for a URL that's gone unreachable — none of which are decided here. Proposing weekly (not daily) refetch, live modules only, with an explicit "source unreachable" state rather than silently skipping — flagged below for sign-off, not decided.
- This is the plumbing Sean's regulatory-webhook idea plugs into: once EU regulatory adapters are added to the existing (currently zero-consumer) `regulatoryIngestDaily` pipeline, a real regulation change can drive `needsReview` directly instead of a dumb calendar timer alone. Building those adapters is separate, content-side work (tracked with the DPP whitepaper effort) — this spec only builds the hook they plug into.

### 4. Stricter approval for web-link sources
- If a section's only `source_refs` entry is a URL (no accompanying human-written rule text beyond what was fetched), the admin UI requires the reviewer to view the fetched snapshot inline before the counsel-review action is enabled — not a blind approval-notes text box.

## Open decisions needing Sean's sign-off

- **Who gets access?** Admin-only (engineers/Sean) today, but RAAS content is meant to be counsel/founder-reviewed — as domain experts like Elise start contributing real content for their verticals, does "admin" need a role tier broader than engineering but narrower than full admin?
- **History storage cost** — full-snapshot-per-mutation is simple and safe but not free at scale. Fine to start with; revisit if module-edit volume grows.
- **Minimum approval-note length for web-link sources** — require at least one substantive line of human judgment, not just a rubber stamp? Proposing yes, flagging for confirmation.
- **Sequencing** — this can be built independently of S52.50 (DPP pipeline) and S52.51 (regulatory whitepaper content), but S52.51's actual authored content has nowhere real to live until this ships. Recommend this before S52.51's content gets written, so real Studio Locker docs replace the thin placeholders directly rather than going through another script.
- **The `workerPromptComposer.js` fix (§1a)** — confirm the proposed `liveSnapshot` approach (serve last-published content during edits, no blackout) before building either it or the naive skip-non-live version. This is the most important open item in this doc: shipping the wrong version of this fix is worse than not shipping a fix at all.
- **Review-status write guard (§1)** — confirm whether to harden the backend (`addSection`/`updateSection`/`removeSection`) to also block `review`-status edits, or accept UI-only enforcement for that case. Recommending the backend hardening, for the same reason `live` is backend-enforced rather than left to the UI.
- **Web-source refetch cadence** — proposing weekly, live-modules-only, with an explicit unreachable-source state (§3). Needs confirmation before build, same as the priority-ranking-style defaults in S52.50.
- **Staleness clock across the edit cycle** — once a live module is deprecated for editing and later republished, does `last_propagated_at` (and any per-section `review_by`) reset, freeze, or continue unaffected? Not yet specified; the right answer likely follows from how the `liveSnapshot` decision above is resolved, so revisit this once that's settled rather than guessing now.
