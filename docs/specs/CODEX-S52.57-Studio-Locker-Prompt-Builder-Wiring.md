## The correction, stated plainly

The original version of this codex claimed: "a document uploaded through the Studio Locker UI has zero effect on any live worker's chat responses, for any tenant, in any vertical, today." **That claim is false, and I should have found the evidence against it before writing it down.**

What actually happened: I found one real injection call site (`index.js` ~4738–4756, reading `services/studioLocker/index.js`) and one real, always-empty collection it reads from, and concluded — without searching the rest of the file for other injection points — that this was *the* production path. It wasn't the only one. A second, separate injection block exists at **`index.js` lines 4483–4496**, calling `getLockerContext()` from `services/sandbox/tenantLocker.js`, reading `tenantLockers/{tenantId}/workers/{workerId}/documents` — **the exact collection the real upload UI (`WorkerLockerPanel.jsx`) writes to.** This block is gated only on `workerPrompt && reqTenantId && workerSlug` — no vertical exclusion, no worker-type exclusion. It runs for every worker, every vertical, every tenant, unconditionally. Per CODEX S52.48 (which found this independently five days ago, with its own citation), this path is already carrying **real, non-demo content** — "already used for real content (e.g. nursing's OpenStax textbook load)."

So: **uploading a document through the Studio Locker panel does reach production chat, today, confirmed by direct code read with line citations.** Sean's original worry — "if we are not actually reading docs in the Studio Locker then the RAAS isn't working" — does not hold for the system a real user actually interacts with. The red team's methodology critique (symbolic search, not just a literal path-string grep; check "which repo") is exactly what surfaced this — a broader, second pass at the same question found what the first pass missed.

**The process failure here is bigger than "didn't grep broadly enough," and naming it once isn't enough.** This is the *second* miss in the same investigation, not the first: first, the original draft didn't search its own target codebase widely enough before concluding a collection was dead. Second — and this is the one worth institutionalizing — a five-day-old draft, CODEX S52.48, had already inventoried this exact landscape in more depth, and this investigation never checked whether an existing codex covered the territory before starting a new one. That's a process gap, not a code gap, and it will recur on the next vertical or the next "is X actually wired up" question unless something changes. There's no formal CODEX-authoring governance doc in this repo to amend (checked — `docs/CODEX-49.1-Execution-Guide.md` is a phase-by-phase execution guide for one specific codex, not a general process doc), so the concrete recommendation is simply: **before scoping a new investigation-style codex, grep `docs/specs/` for the subject matter first** — a `grep -rli` across existing CODEX filenames and a skim of anything that matches, as a mandatory first step, not an optional nicety.

## What's still real — the actual, narrower gap

There is a genuine second system, and it's exactly as broken as the original doc said — the error was only in conflating it with the first:

- **`services/studioLocker/index.js`** (`loadStudioLockerContext`/`getStudioLockerDoc`) reads from `studioLocker/{vertical}/baseline` and `studioLocker/{vertical}/tenants/{tenantId}/documents` — a schema with real criticality tiers (safety-critical/regulatory/operational/reference) and baseline-vs-tenant precedence logic that `tenantLockers` doesn't have. Injected at `index.js` 4738–4756, **but only when `dw.vertical !== "platform"`** — i.e., it runs for real-estate/auto/aviation/nursing-type workers and explicitly skips every Back-of-House worker (accounting/HR/marketing/contacts).
- **Re-verified the "nothing writes to it" claim properly this time**: a symbolic search for `.collection("studioLocker")`/`.collection('studioLocker')` in any form (not just the template-literal path string), across `titleapp-platform`, `sociii-landing`, and `titleapp-admin-ui` (the only three local repos with any code relevant to this system — `sociii-platform` is the confirmed-dead mirror and was checked for completeness only), turns up **zero writers anywhere**. `module.exports` from `services/studioLocker/index.js` contains exactly two functions, both reads. This part of the original finding holds up under the stronger check.
- **The empty-query fallback was checked, and it's not silently dishonest** — `loadStudioLockerContext` always appends a static "Precedence Rules" section regardless of whether any documents exist, and that section explicitly instructs the model: *"When a topic is not covered by any Studio Locker document, say so explicitly rather than inferring from training data... please upload it to your Studio Locker under Company Documents."* No fabricated grounding. **But that instruction is accidentally, not deliberately, honest**: if a user follows it, their upload goes through the *other* panel (`WorkerLockerPanel.jsx` → `tenantLockers`), which does work — but only because two independently-built systems happen to share the word "Studio Locker," not because anyone designed the fallback message to route the user correctly. That's a real architecture confusion, not a false promise, and it's the same problem CODEX S52.48 already named as its core diagnosis: *"worker knowledge/rules grounding is not one system, or four, but at least fourteen."*
- **A different, real silent-truncation risk exists — in the system that actually works, not the empty one.** Checked directly, not assumed: `tenantLocker.js`'s `getLockerContext()` injects the tenant's RAAS system docs first ("so they anchor the context"), then walks uploaded documents **oldest-first** (`orderBy("createdAt", "asc")`), adding each while `total < MAX_CHARS_INJECTION` (600,000 chars) and simply stopping once that's hit — **with no trailing note appended when the overall cap truncates the list**, unlike the per-document `clamp()` function (500,000 chars/doc), which does append `"... [truncated — upload full doc in sections if needed]"` when a single document is cut. So: if a tenant's combined locker documents exceed 600k chars, the **newest** uploads are the ones silently dropped, with nothing in the prompt indicating anything was omitted. This is a genuinely different failure mode from anything in the original claim. **The warn-on-total-truncation fix is safe to build regardless — it only adds a message, changes no behavior.** The reorder-to-newest-first idea is a separate, weaker recommendation that this investigation did not check against the system's own stated design intent: `getLockerContext()`'s comment says RAAS docs are injected first "so they anchor the context," which implies upload *order* may have been treated as meaningful (foundational documents expected early, situational ones later) rather than an arbitrary default nobody examined. Flipping to newest-first without knowing which of those it actually is would be concluding a fix from the code's shape without checking the reasoning behind it — the same category of gap as this document's own original error. Recommend confirming with Sean (or whoever holds that design intent) before reordering; build the truncation warning now, hold the reorder as an open question.
- **Two independent injection blocks stack in the same prompt for non-platform-vertical workers, and neither budget accounts for the other — checked directly.** `tenantLocker.js`'s cap comment is explicit and well-reasoned in isolation: `"Claude's context is 200k tokens (~800k chars); leave ~200k chars for conversation + system prompt + tools"` — 600k chars reserved for locker content. But `services/studioLocker/index.js` reserves its *own*, separately-reasoned `STUDIO_LOCKER_BUDGET_TOKENS = 8000` (~32k chars) on top of that, with no reference to `tenantLocker.js`'s budget, and both blocks fire on the same request (`tenantLocker`'s block runs first at ~4483–4496, `studioLocker`'s runs second at ~4738–4756, both prepending to `workerPrompt`) whenever the worker's vertical isn't `platform`. Today this is harmless in practice only because `studioLocker/{vertical}` is always empty (see above) — its 32k-char reservation is currently spent on nothing but the static precedence-rules paragraph. **The moment any future work gives that collection real content** (which S52.48's own disposition explicitly keeps alive for non-platform verticals), the two budgets — plus whatever the rest of the prompt already spends on own-data grounding, sibling-worker state, workspace identity, and conversation history — have never been checked against each other or against the actual 200k-token ceiling `tenantLocker.js`'s own comment assumes. This needs a combined-budget review before `studioLocker/{vertical}` content is ever populated, not after.
- **One claim from S52.48 not independently re-verified here**: "already used for real content (e.g. nursing's OpenStax textbook load)" is S52.48's own citation, not something this investigation confirmed independently — no seed/load script for nursing OpenStax content turned up in `functions/functions/scripts`, and this investigation has no live Firestore read access (no `gcloud`/application-default credentials in this environment) to check document sizes directly. Flagging as secondhand rather than re-asserting it as freshly verified.
- **This is the same root-cause failure recurring within this document, at smaller scale, and worth naming as such rather than as a one-off correction.** The original error in this codex (concluding a collection was dead without searching broadly enough) and the OpenStax claim above (repeating S52.48's citation as fact, then only downgrading it to "secondhand" after being pressed) are the *identical* failure mode: accepting a claim — whether it's this investigation's own first-pass conclusion, or another codex's citation-shaped sentence — because it came packaged with specifics, not because it was independently checked. The lesson from this document is not "the OpenStax fact happened to be unverified" — it's that **a citation from another codex needs the same verification bar as a claim about the code itself**, and that bar wasn't applied consistently even inside a document whose whole premise is applying it.

## Live cost of the dead system — verified, and distinct from the correctness findings above

Separate from whether `studioLocker/{vertical}` produces wrong or missing *content* (it doesn't produce anything, see above): the injection block at `index.js` 4738–4756 fires on **every chat turn for every non-platform-vertical worker**, which means it has been executing a Firestore read against a guaranteed-empty collection since it shipped (commit `3ee711a0`, 2026-08-01) — real latency and real read cost, on every such request, for a result that's always just the static precedence-rules paragraph. This is fully verified from evidence already established above (the block is unconditional on vertical, the collection has zero writers) — it needs no new investigation, just its own line item, because it's a cost question, not a grounding question, and conflating the two would understate a very concrete, present-tense, quantifiable waste (proportional to real non-platform-vertical chat volume) as if it were just theoretical risk alongside everything else in this section.

## Calibration note: urgency of the truncation and budget-stacking findings

Both the total-injection silent-truncation gap and the unreconciled combined budget (above) are stated as needing resolution "before, not after" `studioLocker/{vertical}` gets populated. That's correct for the budget-stacking item, which is genuinely dormant until that specific future event. **It should not be read as a claim that the truncation gap is currently firing for a real tenant** — this investigation did not check whether any `tenantLockers` collection today actually holds anywhere near 600k combined chars (no live Firestore access, as noted above), so whether this is a live bug or a correctly-identified-but-still-latent one is genuinely unknown, not just unstated. Treat it as **structurally real and worth fixing, not confirmed to be actively truncating anyone's documents right now** — asserting otherwise would repeat, at a smaller scale, exactly the over-claiming this document exists to correct.
