**Status:** SCOPED (2026-08-16), not built. Written up at Sean's explicit request after live-testing `/demo/title` and finding the Vault renders the personal "Four Pillars" layout for a business workspace (ABC Title Company / Sarah Garris) with no business-organized alternative.

## Why this exists

Sean's framing, live: *"A person needs the vault as structure, but a Company needs it organized more by clients, customers use cases, audit requirement... We need to update the business demos with a business vault, not the personal vault."*

Sean recalled a prior discussion (2026-08-15, "yesterday") that went deep on this, including a "minting issue" and "how wallets would be organized vs. the actual vault presentation" — and believed it got lost in the shuffle. **I have no record of that discussion** — checked persistent memory, `docs/specs/`, recent git log, **and chat history** (an independent conversation search across 2026-08-15 turned up nothing on the vault/wallet topic — the only 8/15 conversation on record is the CODEX 71 DPP red-team and balance-sheet review); nothing matches across any of the four channels. Where the code itself independently surfaces something that sounds like the wallet/minting tension Sean remembers (see below), it's called out — but treat that as a fresh finding, not a recovered one.

## What already exists to build on

- **Personal Vault, fully built**: `apps/business/src/sections/VaultDTCs.jsx` + `apps/business/src/data/useDtcCatalog.js`. Four Pillars (My Stuff / My Money / My Health / My Education), a single net-worth rollup, six-class asset taxonomy (`ASSET_CLASSES` includes "Business Records" and "Compliance" as declared classes — see gap below).
- **The backend already supports non-personal, tenant-scoped DTCs** — this is not a green-field build. `functions/functions/services/vault/vaultWriter.js` `mintDtc()`: when `tenantId` is a real workspace (not `"vault"`/`"personal"`/the uid), it sets `modification_authority: "workspace_role:admin"` instead of `"owner_only"`. The role-gated write path (`appendEvent()` → `enforceRoleGate`) already exists and is exercised for non-personal DTCs. The gap is entirely in what queries and renders — not in what the write path supports.
- **A real client/matter unit already exists for the title vertical**: `titleOrders` (seeded in `functions/functions/scripts/demo/seedTitleDemo.js:299-370`), tenantId-scoped, one doc per transaction — `address`, `parcelId`, `county`, `buyerName`, `sellerName`, `status` (`search_complete`/`commitment_issued`/`exam_in_progress`), `riskScore`, `defectCount`/`defectNote`. This is the natural "matter" axis Sean is describing — it doesn't need to be invented, only joined to the Vault.
- **Drive files already link to a matter**: `DRIVE_FILES` in the same seed script carry `orderId` (e.g. `title_drive_001` → `title_order_001`). DTCs don't have an equivalent field today (see gap below), but the pattern of "record → orderId" already exists one collection over.
- **The Logbook is already a generic, append-only audit trail** — `logbookEntries`, keyed by `dtcId`, written by `vaultWriter.appendEvent()`. Nothing new needed here for "audit requirement" — a business Vault's per-matter audit trail is the same substrate the personal Vault already uses.

## What's missing — real gaps

- **The frontend hard-codes the personal tenant — it cannot query anything else.** `useDtcCatalog.js:78,93`: `const PERSONAL_VAULT_TENANT = "vault"; ... headers["x-tenant-id"] = PERSONAL_VAULT_TENANT;` — verified directly, not inferred. The comment on that constant explicitly documents this as intentional current behavior ("MY VAULT is 'my stuff only' — ALWAYS the personal vault, never the active business persona/workspace"). That's the right call for the personal Vault and shouldn't change — but there is currently **zero** code path that queries DTCs by any other `tenantId`, so a business Vault view doesn't just need new UI, it needs a new query.
- **A real, live demo bug, found while grounding this doc**: `seedTitleDemo.js`'s own section comment reads `// ─── 5. Vault DTCs — company assets ───` (line 372) — the seed author's intent was clearly business/company assets (E&O insurance, a $847,200 escrow/trust account, a $38,450 operating account, the TDI title license, a notary commission, the office lease). But every entry in that `DTCS` array is written with `tenantId: "vault"` (line 558) — the **personal** tenant. Today, in the live demo, ABC Title Company's $847,200 client escrow/trust balance and $38,450 operating balance render inside Sarah Garris's *personal* "My Money" pillar, contributing to her *personal* net worth. This isn't a cosmetic mislabel: escrow/trust account segregation for Texas title agents is a real statutory requirement, not the demo's own flavor text — **Texas Insurance Code Chapter 9** (title insurance trust-fund provisions) and the **TDI Basic Manual of Title Insurance, Section V** (escrow accounting rules) require entrusted funds to be held in a bank account "separate from all other funds," specifically marked as an escrow/trust account, and subject to its own audit. (Verified via [tdi.texas.gov/title/titlem5a.html](https://www.tdi.texas.gov/title/titlem5a.html) and the Chapter 9 trust-fund summary at [nititle.com](https://www.nititle.com/sites/default/files/static/abp2tx.pdf) — not the seed data's own description text, which is not a regulatory source.) The current demo shows exactly the commingling that requirement exists to prevent.
- **A second, smaller mapping gap in the same data**: `ASSET_CLASS_OF` in `useDtcCatalog.js` has no entries for the `insurance`, `license`, or `equipment` DTC types the title seed data uses — so `assetClassOf()` falls through to its default (`"Personal Assets"`, line 67). The E&O insurance policy, the TDI title license, and the notary commission all currently render under the same "💎 Personal Assets" tab as watches and jewelry, not under "Credentials" or the declared-but-unused "Business Records"/"Compliance" classes.
- **No DTC-to-matter link exists.** `mintDtc()`'s schema has no field for "which titleOrder/case/client this record belongs to" — `parent_dtc_id` exists but is for DTC-to-DTC version lineage, not for linking a record to a business transaction. Grouping by client/matter requires adding one.
- **Minting is single-wallet today, with no per-tenant separation** — this looks like the strongest candidate for what Sean recalled as "the minting issue." `functions/functions/services/minting/crossmintMinter.js`'s own header comment: *"v1 mints to a server-managed recipient (configurable via `CROSSMINT_RECIPIENT`, defaulting to email:treasury@sociii.ai which Crossmint resolves to a managed wallet). Future per-user or per-tenant recipient routing is a Phase 2 concern."* Every DTC, from every user and every business tenant, mints to the same one custodial wallet today. There is no code path anywhere for a business tenant to have its own wallet/custody boundary distinct from another tenant's, or from personal DTCs. A business Vault surfaces *whose* records these are far more visibly than the personal Vault does — which makes this pre-existing gap more exposed, not something this spec can quietly ignore.

## Proposed shape (for review, not yet built)

1. **New business-tenant query path.** Add a second hook (or parameterize `useDtcCatalog`) that queries `/v1/dtc:list` with `x-tenant-id` set to the active *business* workspace's real tenantId instead of the hardcoded `"vault"` constant. Personal Vault's behavior does not change — it stays unconditionally pinned to `"vault"` per the existing, deliberate design.
2. **New `linkedRecord` field on DTC metadata** — generic, not title-specific: `{ linkedRecordType: "titleOrder", linkedRecordId: "title_order_003" }`. Title orders are the first target. **Caveat on generalizing further**: the field name is vertical-agnostic, but "primary grouping = client/matter" (point 3) is not guaranteed to transfer as-is — a DPP business tenant's natural axis is a product/SKU or batch (`dppProducts`), not a client/matter the way a title order is. Treat "matter-first" as the title vertical's specific answer to a more general question ("what's this business tenant's primary organizing unit"), and re-derive that answer per vertical rather than assuming every business Vault groups by client/matter.
3. **Business Vault view, organized by matter first (title vertical)**: primary grouping = open client/matters (from `titleOrders`, joined via `linkedRecordId`), each showing its own DTCs + its own Logbook as that matter's audit trail. A secondary "Company Records" section (not a Four-Pillars tile) holds entity-level assets with no `linkedRecordId` — E&O insurance, the TDI license, the office lease, and the **operating account only**. The escrow/trust account is never placed in Company Records — see point 4, it gets its own surface, specifically to avoid the two sections disagreeing about where client funds live.
4. **Escrow/trust funds get their own explicit surface, excluded from Company Records and from any net-worth rollup.** Labeled distinctly (e.g. "Client Trust — funds held for others, not company assets") so the UI itself enforces the same separation Texas Insurance Code Chapter 9 requires, rather than relying on a human to remember not to add it up or not to file it next to the operating account.
5. **Read-side access, at least named even if full RBAC is deferred.** The write path already has a role gate (`workspace_role:admin`, existing); nothing today says who can *see* a business tenant's trust balance, Company Records, or other staff's assigned matters — and for a title/escrow business this isn't cosmetic, it sits next to the RESPA/Affiliated Business Arrangement sensitivity already on record for this vertical. Minimum proposed default: Company Records and the trust-account surface are admin-only; a matter's DTCs/Logbook are visible to admins plus whichever staff member(s) are assigned to that specific `titleOrder`. Full role granularity can come later, but "everyone in the workspace sees everything" should not be the shipped default even for a demo.
6. **Data correction, independent of the new UI**: re-tenant `seedTitleDemo.js`'s `DTCS` array from `tenantId: "vault"` to the real `TITLE_TENANT`, and extend `ASSET_CLASS_OF` to cover `insurance`/`license`/`equipment` (into "Credentials" or "Business Records"/"Compliance" as appropriate) — this is a real bug regardless of whether the new business Vault view ships.
7. **Coexistence, not replacement.** Business Vault appears as a new destination in a business workspace's nav (workspaces already switch this way today); Personal Vault stays exactly where and what it is now.

## Open decisions needing Sean's sign-off

- **Generic `linkedRecordType` field, vertical-specific grouping axis** — recommending the generic field, but confirm the grouping axis is re-derived per vertical (not assumed "matter-first" everywhere) per the caveat in point 2 above.
- **Escrow/trust exclusion from net worth and from Company Records** — recommending yes, now backed by Texas Insurance Code Chapter 9 / TDI Basic Manual Section V (real citations, not the seed data's own text — see gap above). This is the one item in this doc I'd push back hardest on shipping any other way.
- **Read-side access defaults** — recommending admin-only for Company Records + trust surface, matter-assigned-staff-only for individual matters, per point 5 above. Confirm before this is shown to anyone outside the team, given the RESPA/ABA sensitivity already flagged for this vertical.
- **Activating "Business Records"/"Compliance" as real asset classes** — they're already declared in `ASSET_CLASSES` but nothing maps to them (`ASSET_CLASS_OF` has zero entries for either). Confirm they're the right home for insurance/license/equipment-type records rather than a new class.
- **Minting/wallet separation — in scope here or explicitly deferred?** Recommending **deferred as its own follow-up** (it's already flagged as Phase 2 in `crossmintMinter.js`, not new scope creep from this doc), **with a concrete un-defer trigger**: before this demo (or any business Vault view) is shown to any external title-vertical stakeholder, prospect, or Reg CF material — not left open-ended. Once escrow is a labeled, separate line item instead of buried in a personal pillar, "which wallet actually custodies this" becomes a foreseeable question with no good current answer (single shared custodial wallet, `treasury@sociii.ai`, for every user and every tenant).
- **Rollout order** — title vertical first (real seed data + `titleOrders` already exist) vs. generalizing for other business tenants (DPP, etc.) at the same time. Recommending title-first, same sequencing logic as S52.50/S52.52.
