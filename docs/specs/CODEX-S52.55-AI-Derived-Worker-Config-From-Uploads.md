## Why this exists

Sean's correction on S52.54's first draft: *"The sandbox is a bit too much for a teacher with no code or experience to use. We need to make it simpler and easier to upload courses."* The fix that answers this — upload materials, answer a few plain-language questions, AI derives the rest, get a working worker back — isn't specific to teachers or to education. Any non-technical creator in any vertical has the same problem with the current 9-step `WorkerSandbox` flow (Define → Design → Knowledge → Rules → Tools → Test → Preflight → Distribute → Grow). This scopes that capability once, generally, rather than building a one-off inside the education demo.

## What already exists to build on

- **The 9-step flow itself** — `apps/business/src/pages/WorkerSandbox.jsx`, backend `functions/functions/services/sandbox/workerBuildFlow.js`. Real, working, not education-specific.
- **The Knowledge step's file upload already exists** — `FileUploadBar.jsx` + `classifyFile()`. Uploading materials is step 3 of 9 today; nothing new needs building for upload itself.
- **A real, structured safety-test protocol already exists at the Test step (step 6)** — `functions/functions/services/sandbox/workerTestProtocol.js`, explicitly documented as "the AHA moment red-team session": five mandatory questions Alex asks of every built worker before it's considered validated:
  1. **RAAS Tier 2 enforcement** — does the worker refuse an action its own rules forbid?
  2. **Knowledge currency** — does it know about a recent change in its vertical?
  3. **Escalation behavior** — what does it do when a subscriber is about to make a serious mistake?
  4. **Depth of knowledge** — a vertical-specific edge case.
  5. **Intellectual honesty** — what does it admit it doesn't know?
  Each response gets classified `clean | flagged | escalated | failed` (`RAAS_CLASSIFICATIONS` in `workerTestProtocol.js`).

## What's missing — real gaps, verified directly (not assumed)

- **The Test step's classification is creator-supplied today, not independently evaluated.** Direct quote from the file's own header comment: *"Classifies each response as clean / flagged / escalated based on **creator-supplied (or future automated) RAAS evaluation**."* Automated evaluation is explicitly future work — today, whoever is building the worker grades their own worker's answers to the five red-team questions. That's a reasonable trust model for a technical creator who understands what "RAAS Tier 2 enforcement" means and has a reason to grade honestly. It is a materially weaker check for a non-technical user who may not recognize a bad answer as bad — which is exactly the audience this fast path is being built for.
- **Preflight (step 7) is a business/monetization gate, not a safety gate — verified directly, correcting an earlier draft's assumption.** The actual seven gates (`PREFLIGHT_GATES` in `apps/business/src/components/sandbox/worker/canvases.jsx`): *Creator agreement signed, Identity verified, Payout account connected, Tax forms on file, Worker spec reviewed, Knowledge base passes minimum threshold, Admin review approved.* This is KYC/payout/tax/marketplace-listing readiness. "Worker spec reviewed" and "Admin review approved" are the only two with any safety-adjacent character, and both are self-certified checkboxes today, not an automated or independently-verified check.
- **No mechanism exists today for a fast path to require something the 9-step flow doesn't already have** — i.e., there's no "extra scrutiny for AI-derived, non-technical-creator-built workers" concept anywhere. If a fast path is built without addressing this, it inherits the weakest link (self-graded Test) with less human attention on top of it (the whole point of removing steps), not more.
- **"Admin review approved" is not a real backend checkpoint — verified directly, correcting the first draft of this doc's own §5.** `PreflightCanvas` (`canvases.jsx:1152-1195`) tracks all seven gates as one client-side `Set` the creator checks off themselves; on completion it submits `{ stepData: { gatesPassed: PREFLIGHT_GATES.length, visibility, ... } }` — a flat count, with no distinction for which gate, no admin-role check, no separate approval route anywhere in `workerBuildFlow.js`. "Admin review approved" is exactly as self-flippable as "Tax forms on file." There is currently no code path where an actual human admin reviews anything before this checkbox gets checked.
- **The `escalated` classification has zero runtime existence outside the Test step — verified by grep across the whole backend, not assumed.** It's defined and used only in `workerTestProtocol.js` (`RAAS_CLASSIFICATIONS`, and the keyword match that suggests it during test grading). It never appears in the live chat-handling code (`index.js`'s `chat:message` route or anywhere else). So today, a live, in-production worker interaction has no equivalent classification or notification path at all — `escalated` is purely a one-time, pre-publish, build-flow concept. There is nothing to correct here because there is currently nothing built.

## Proposed shape (for review, not yet built)

1. **Upload-first flow**: creator uploads materials (any format the Knowledge step already accepts), answers a small number of plain-language questions specific to what they're building, AI derives Define/Rules/Tools from the combination.
2. **A mandatory plain-language confirmation step before publish** — not folded away, not skipped: "here's what I set up, in plain language, does this look right?" This is the point where a non-technical creator can catch an AI misread without needing to understand RAAS, rules syntax, or tool schemas.
3. **The five-question Test protocol still runs, unconditionally, on every fast-path worker** — this is not one of the steps that gets simplified away, and it shouldn't be, since it's the one existing safety-relevant mechanism in the whole flow.
4. **Independent evaluation of the Test protocol's five answers, for fast-path-built workers specifically** — since self-grading is a weaker check for exactly the audience this path serves, propose the fast path be the first place "future automated RAAS evaluation" (already named as a gap in the existing code's own comments) actually gets built, rather than continuing to defer it. This does not need to block the fast path's initial ship if scoped as a fast-follow, but it should be named now, not discovered later.
5. **Recommend fast-path workers default to `organization-only` visibility** (per the existing `VISIBILITY_OPTIONS`) rather than `public` — this limits *who can reach* the worker (fewer strangers) independent of any review question. **Caveat, not a full mitigation**: it does nothing to limit harm to people already *inside* that organization — for the K-12 forcing-function case, the students are already inside the org. Don't treat this as sufficient on its own for every vertical this generalizes to; it's one real, cheap control, not the control. **This is NOT the same thing as "gated by admin review" and the doc's first draft wrongly implied it was** — see the gap above: "Admin review approved" is a self-flippable checkbox today, not a real human checkpoint, so it cannot be the interim safety net for fast-path workers until it actually is one. Building a real admin-review gate (a genuine backend check requiring an actual admin-role action, not a client-side checkbox) for fast-path-built workers specifically is therefore its own real piece of work, not a "just don't skip the existing gate" instruction — because there's no functioning gate to not-skip yet.

## What was actually built

- **Real admin-review gate — option (a), all four named pieces**: `services/sandbox/workerReviewGate.js`. (i) `enforceRoleGate`-backed `submitReview`/`handleList`/`handleDecide`, plus — the piece that makes it actually real, not cosmetic — **`index.js`'s chat handler now refuses to serve a `buildSource:"fast-path"` worker unless `digitalWorkers/{slug}.status === "live"`**, verified this didn't exist before (any digitalWorkers doc served unconditionally on `dwSnap.exists`, no status read anywhere in that path). (ii) `WorkerReviewQueue.jsx` — no longer a bare slug-and-approve-button; `handleList` now joins the real worker content (job, knowledge summary, full judged test transcript) so an admin has something to actually evaluate. (iii) a real SLA: `checkStaleWorkerReviews` (daily cron) emails a tenant's admin once per review pending over 24h — not just a UI timestamp nobody's watching. (iv) review criteria: the admin sees the derived spec's job/knowledge-summary plus the independently-judged test transcript (see below) — enough to judge "does this match what was uploaded" without needing to have built it themselves.
- **Independent RAAS evaluation — point 4, no longer deferred.** `judgeAnswer()` in `teacherFastPath.js` replaces keyword-matching self-grading with a genuinely separate model call, given the question + answer + the worker's own configured rules, explicitly told not to trust the worker's self-description. This fixed a **real, empirically-found flaw** in the naive keyword approach, not a hypothetical one: testing the water-cycle worker, the keyword heuristic classified 3 of 5 answers `escalated` simply because the worker *honestly described its own escalation policy* when asked about it — not because anything was actually escalated. Re-run with the independent judge: all 5 correctly classified `clean`, each with a one-sentence reason distinguishing "described the policy" from "violated the policy." Verified via a direct test run, not asserted.
- **Live escalation infrastructure pulled forward, shipped alongside the fast path** (not deferred) — `services/sandbox/liveEscalation.js`, screening every worker's every chat turn (not fast-path-only — generic per the recommendation below), writing a record and emailing an admin on a real hit. Also empirically corrected during testing: the first abuse/neglect pattern only matched pronouns ("he hits me") and missed how a child actually phrases it ("my dad hits me") — expanded to cover common family/guardian relation words after finding the gap via direct test cases, not by inspection alone.
- **Default visibility — found unwired while writing this doc, then fixed in the same pass.** `teacherFastPath.js` didn't set a `visibility` field on the worker doc at all, which — per `catalog:byVertical`'s own filter logic, verified directly — reads as effectively public once live, not organization-only. Added `visibility: "organization"` (the real id per `VISIBILITY_OPTIONS`, not `"organization_only"` as an earlier draft of this doc guessed) plus `internal_only: true` to the write. Not yet re-verified against a live fast-path-built worker in the catalog after this specific fix — the water-cycle worker built earlier in this session predates it, so a fresh build should be spot-checked before trusting this is fully closed.

## Open decisions — what's still genuinely open
- **The independent judge is itself an LLM call, not a formally verified system** — it's a real, meaningful upgrade over keyword-matching, but it can still be wrong, and nothing currently checks the judge's own output against a second, different signal. Treat it as a much stronger first pass, not a provably complete one.
- **Which verticals get this first** — education (S52.54) is the forcing function and the only vertical exercised so far. Generalizing beyond it is unstarted.
