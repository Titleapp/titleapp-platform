# CODEX S52.56 — The Garcia Scenario: Making the Customer-Facing Portal Real (Scope Only — Not Yet Built)

**Status:** SCOPED (2026-08-20), not built. Written at Sean's request after realizing the demo/title video only shows the operator (ABC Title / Sarah) side — there's no working walkthrough of what the actual customer (title buyer) sees.
**Author:** Sean Lee Combs + Claude Code
**Running example:** "Mr. Garcia" — a customer closing on a condo in Texas through ABC Title Company. Used throughout as the concrete persona; the shape generalizes to any vertical's end-customer (a vet's pet owner, an advisor's investor, etc.) the same way `ClientPortal.jsx` already does today.
**Predecessor:** None directly, but this builds on top of two things already in flight: the Vault Team+Transactions folder restructure (today's parallel demo/title fixes), and CODEX S52.57 (Studio Locker wiring) — **correction after re-verification, see §5**: the dependency originally stated here was wrong. The universal Studio Locker injection (`tenantLockers` → `index.js` ~4483–4496) runs for every worker unconditionally, with no vertical or worker-type gating — so a Garcia chat routed through the standard worker-chat pipeline gets real ABC Title grounding automatically, with no Studio Locker fix required first. §5 below is corrected accordingly.

## Why this exists

Every demo and video walkthrough so far shows the **operator** side: Sarah at ABC Title, her COMPANY VAULT, her workers, her chat. Sean's point: a title company's actual product isn't Sarah's dashboard — it's what a **buyer or seller experiences during their closing**. Without that view built and tested, "my videos only show half the story." He's right, and it's a real gap, not a nice-to-have: the customer-facing side is the thing an actual title company would pay for.

Sean's framing: this should mirror the **student view** pattern already established elsewhere in the platform — a **Personal Vault** plus scoped tools, landed into directly (confirmed: `App.jsx` already has a real "land the user directly in their Personal Vault" code path, `WORKSPACE_NAME = "Personal Vault"`, for individual/consumer-type users, distinct from an operator workspace). Mr. Garcia should get that same shape, but scoped to *his* relationship with ABC Title: a chat/worker grounded in ABC Title's own Studio Locker and rules, that can discuss his closing, records, offers, and give advice — and a Vault showing his property (and related personal property) once it's his.

## What already exists to build on

- **`ClientPortal.jsx` already exists and is closer to done than "zero."** It's explicitly documented in its own header as "the white-label, customer-facing surface... Door 2 in its purest form." It already has:
  - A working `/portal?company=...&persona=...&orderId=...` routing scheme, with a real skin already defined for **`attorneys-title` = "ABC Title Company," tagline "Henderson County, Texas — Athens, TX"** — this is not a hypothetical, it's the exact company Sean's been testing.
  - `buyer` and `seller` personas already scaffolded (currently fixture identities: "Sara Kahele," "Troy Garris" — stand-ins for what would be Mr. Garcia). The file's own comment labels these "demo identities... in production these are matched from the operator's CRM," consistent with them being invented placeholders rather than references to anyone real — **flagging for Sean's explicit confirmation before either name appears in any externally-shared video or artifact**, since that's a judgment call about real people, not something verifiable by reading code.
  - A `TitleVaultCanvas` component that already renders a Vault-style document view ("Recorded Deed," "Owner's Title Policy," described as "hash-anchored... yours to keep forever").
  - A real, live backend call for the *advisor* persona specifically: `POST /v1/ir:advisor:step` mints an actual DTC into that person's Vault on affirm. So the "mint a real record into a customer's personal Vault" mechanism exists and works for at least one persona today — it's a pattern to extend, not invent.
- **The Vault folder restructure happening in parallel today** (Team + Transactions groups, one folder per deal named `{order code} — {property address}`) is exactly the shape Mr. Garcia's own Vault should mirror one level down — his Vault shows *his* transaction folder (and nothing else), not ABC Title's whole Team+Transactions tree.
- **`contracts/capabilities.json`** is described in `CLAUDE.md` as "the source of truth for all executable actions... if a capability is not declared there, it does not exist" — but **checked directly against the file itself, that description overstates the file's current status.** Its own header is explicit: `"_enforcement": {"status": "design_doc", "runtimeEnforced": false}`, with the note *"Routes in index.js do not check this registry before executing... Currently descriptive, not enforced,"* and its own `no_undeclared_endpoints` principle is labeled `"INTENT ... Currently descriptive, not enforced"` — enforcement is explicitly targeted at a future v2.0.0 (current version: 1.1.0, 2026-06-28). **Correcting an earlier draft of this doc**, which asserted `ClientPortal.jsx`'s scripted buyer/seller answers were "already out of spec" with this rule as a pre-existing violation: that framing was wrong, because *nothing* on this platform is currently held to this rule as enforced — singling out the scripted portal answers as non-compliant implies every other route that isn't in this registry is equally "violating" something, which isn't a meaningful claim while the file is self-described as intent-only. What's still true and worth keeping: no capability exists today for any customer-facing title action (grepped every declared id for anything status/closing/record-related — only generic, non-title matches like `kyc.get_kyc_status_v1` and `dtc.create_dtc_record_v1` exist), so **new** customer-facing actions this portal takes should still be declared here as good practice, consistent with stated intent — just not framed as fixing an enforced violation that doesn't currently exist.

## What's missing — real gaps, verified directly, not assumed

- **Buyer/seller chat in `ClientPortal.jsx` is entirely scripted, not live.** Verified directly: the buyer/seller reply logic is regex keyword-matching against a hardcoded `SCRIPTS` object (e.g. `if (/vault|record|document|file/.test(t)) return "<canned string>"`) — there is no call to any real chat/completion endpoint for these two personas. Contrast with the advisor persona, which does make one real backend call (`/v1/ir:advisor:step`). **This means today's buyer/seller demo is a dialogue tree, not a worker.** Making it real means routing buyer/seller messages through the actual tenant chat pipeline (the same `workerPrompt` assembly path used everywhere else in the app, index.js's worker-chat handler), not writing more canned scripts.
- **No real per-transaction data — fixtures only.** "Sara Kahele" / "Troy Garris" and the `TitleVaultCanvas` document list are hardcoded in the file. There's no wiring from an actual case-file record (the transaction folder from the Vault restructure) to what the portal shows. Mr. Garcia's portal needs to read *his* actual order/closing record, not a fixture.
- **No entitlement check on `orderId` — verified, not assumed.** `orderId` is read straight from the URL query string (`params.get("orderId")`) and only ever *displayed* (truncated) — nothing in the file checks that the authenticated user (or even an anonymous visitor) is actually the buyer/seller on that specific order. Today this is harmless because the data behind it is fake. **The moment this becomes real, an unauthenticated or wrong-party visitor could view another customer's closing by guessing or reusing a link** unless an entitlement check is added. This has to be designed before real data flows through this surface, not bolted on after.
- **No defined scope boundary between "Mr. Garcia's view" and "ABC Title's view."** The codex needs to state explicitly: Mr. Garcia can see his own transaction folder and its documents, his chat history, and general (non-confidential) guidance — he should *not* see other clients' case files, ABC Title's internal Team folder (E&O insurance, notary commission, operating accounts), or other customers' Vault contents. This is a real permission model, not just a different URL.
- **No regulatory research on the advice/UPL boundary — checked directly, genuinely not done, not something to build against a guess.** Texas title already has real, existing RAAS content in this repo: `raas/real-estate/TX/title-production.md`, `disclosures.md`, `licensing.md`, `contracts.md`. Checked all of them directly for unauthorized-practice-of-law boundary language (what a non-attorney title company employee — or a chat — can and can't say to a customer as "guidance" vs. "advice") — **none of these files contain any UPL-specific language today.** Given Sean's own standing rule that compliance citations must be real and verifiable, and given this platform's prior real friction with title-industry regulatory resistance: **do not write customer-facing "advice" language into Mr. Garcia's chat until real UPL/Texas Department of Insurance research is done and cited**, extending the existing TX ruleset files above rather than inventing a new one. Until then, keep this chat's scope to process/status information only (see open decisions below).
- **Dependency on Studio Locker corrected after re-verification — see CODEX S52.57.** The original claim here (that this codex blocks on a Studio Locker fix) was wrong. The universal Studio Locker path (`tenantLockers` → `index.js` ~4483–4496) runs for every worker unconditionally — so a Garcia chat routed through the standard worker-chat pipeline is grounded in ABC Title's real uploaded documents automatically, no fix required. What ABC Title has actually uploaded there today (if anything) is a separate, ordinary question — not a wiring gap.

## Proposed shape (for review, not yet built)

1. **Route buyer/seller messages through the real chat pipeline**, scoped to a restricted capability set — newly declared in `contracts/capabilities.json` (today: zero customer-facing title capabilities exist, see above) — deliberately narrower than what an ABC Title operator's chat can do, and scoped at launch to process/status information only, not advice (see the UPL gap above). Grounding comes for free from the existing universal Studio Locker injection; no separate wiring needed for that part.
   - **Important limit on that capability-scoping, flagged by the red team and correct: capabilities.json governs what the chat can *execute*, not what injected grounding text can *say*.** Restricting Mr. Garcia's chat to a narrow capability set stops it from *taking* actions outside that scope, but it does nothing to filter the *content* of whatever Studio Locker documents ABC Title has uploaded — those are just text prepended to the prompt (see CODEX S52.57), read verbatim by the model regardless of how narrowly the chat's executable capabilities are scoped. If an uploaded document (an internal SOP, a training manual, anything in the "already used for real content" pattern S52.48 describes) contains advice-flavored language, a capability restriction alone will not stop the model from surfacing it to a customer. This needs either a content-level distinction between operator-facing and customer-facing grounding sources (not all uploaded documents should be visible to Mr. Garcia's chat, only ones ABC Title marks as customer-appropriate), or an explicit, named acceptance of this as a residual risk pending whatever review-gate CODEX S52.52 already proposes for above-reference-tier content generally. Silently assuming the capability restriction alone handles this would be the wrong call.
2. **Real per-transaction data and the `orderId` entitlement check are one atomic requirement, not two sequential steps — must ship in the same release/PR, never one without the other.** Backing `TitleVaultCanvas` (and a customer-scoped records/offers view) with the real transaction folder from the Team+Transactions restructure, without also gating it behind proof that the requester is actually the buyer/seller on that order, recreates exactly the exposure this codex warns about: real closing data reachable by anyone who has or guesses the `orderId`. If engineering pressure or parallel workstreams would otherwise let these drift apart, that itself is a reason to treat them as one PR, not a schedule to manage around.
   - **The entitlement check itself must not become an enumeration oracle.** A failed lookup for "wrong party, real order" and a failed lookup for "order doesn't exist" must return an indistinguishable response — same status code, same generic message, same response timing (no early-return on the cheaper check). Without this, the entitlement check that's supposed to close the exposure becomes a tool an attacker can use to enumerate which `orderId`s are real, even without ever seeing the underlying closing data. Small to build, invisible until someone actually probes for it, and easy to get wrong by accident (e.g., a natural-looking `if (!order) return 404; if (order.buyerId !== uid) return 403;` implementation leaks exactly this distinction through the status code alone).
3. **Reuse the existing DTC-mint pattern from the advisor persona** (`/v1/ir:advisor:step` as a model) for whatever "this becomes officially Mr. Garcia's" moment is in a title closing (e.g., recording) — a new, title-specific endpoint following the same shape, not a new mechanism invented from scratch.
4. **Explicitly test this as its own persona in QA**, the same rigor as any other demo persona walkthrough (and per the sequential-demo-QA constraint already in effect for this platform — a customer-facing session shares the same `sociii.ai` browser storage as operator/creator sessions, so it can't be tested in parallel with them either).

## Open decisions needing Sean's sign-off

- **Identity/entitlement mechanism** — how does "Mr. Garcia" prove he's Mr. Garcia for this specific order? Authenticated account matched by email/phone from ABC Title's CRM (mirrors how `ClientPortal.jsx`'s own header describes identity matching for the vet/advisor personas today), a signed/expiring link ABC Title sends him, or both? This is the single most important open item — nothing else here is safe to build against real data until this is answered.
- **Exactly what "related personal property" means for title specifically** — is this just the property being purchased, or does it extend to e.g. a HELOC, prior property, or other holdings tied to the same buyer? Scope this narrowly (just this transaction) unless Sean wants more.
- **What advice, specifically, can this chat give?** "Advice" was in Sean's own framing. Given the confirmed absence of any UPL/TDI research today, recommend launching with process/status guidance only (safe, and what most of the existing scripted replies already do) and treating anything that could read as legal/closing advice as explicitly out of scope until real regulatory research exists — not "once that module exists" as a vague future gate, but as a concrete precondition with its own citation requirement, same standard as everywhere else on this platform.
- **Does this replace or run alongside `ClientPortal.jsx`'s existing scripted flow?** Recommend extending the same file/route rather than a parallel build — the skin system, routing, and Vault-canvas shell are all reusable; only the chat backing and data source need to go from scripted to real.
- **Combined sequencing across all three related codices** — S52.52 (RAAS admin module), S52.57 (Studio Locker — corrected: mostly already works, residual gap is real but narrower than first stated), and this one each name only their immediate predecessor, which risks each getting scheduled independently and stalling on "waiting for the other." Stated together: **this codex (Garcia) is no longer blocked on S52.57** — the grounding it needs already works. It's still blocked on its own open items above (entitlement mechanism, capability declaration, UPL research). S52.52 and S52.57's residual item (folding the correction into S52.48) are independent of Garcia and can proceed on their own schedule.
