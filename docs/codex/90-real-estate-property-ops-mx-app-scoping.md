## 1. Executive Summary

- **This is not a greenfield feature, but "consolidation-and-completion" undersells the actual scope — read this as sizing guidance, not a promise of small effort.** A comprehensive property-manager worker spec already exists (**CODEX 23**, `docs/codex/23-property-manager-worker.md`) covering operator/tenant modes, Fair Housing and eviction rules, an MX lifecycle, and a canvas spec — written months ago, largely unbuilt. A second doc (**CODEX 27**, `docs/codex/27-picture-first-input.md`) already proposed the exact photo-first MX-ticket schema and reserved three capability IDs for it — also unbuilt. But by the time §4's sequencing is laid out, the real work list includes a new capability namespace, a schema migration that also redesigns its own photo fields, a new persistence architecture, a platform-wide (not vertical-scoped) role/permission overhaul, and four new UI surfaces — two of them (buyer/lessor walkthrough, building inspector) for actors CODEX 23 never modeled at all. That's closer to a new vertical build that happens to reuse some plumbing than a quick cleanup — size expectations accordingly.
- **Three disconnected "maintenance" implementations already exist in the repo, and none of them talk to each other.** (1) A top-level `maintenance` Firestore collection with a real REST API, but it's API-key-gated and exported as a separate integration-only Cloud Function, not called by any UI. (2) A richer `tenants/{id}/maintenanceTickets` subcollection with a full photo-lifecycle schema, but it's written only by a demo seed script and read by nothing. (3) Three React canvas components (tenant portal, property-manager dashboard, a maintenance kanban board) that are fully hardcoded demo data — the "Submit" and "Pay Now" buttons have no click handlers at all. Building this product means picking one of these three and wiring it end-to-end, not adding a fourth.
- **Zero capabilities exist today for real estate, property management, maintenance, rent, lease, or inspection** in `contracts/capabilities.json` — a hard zero, not a partial build. Aviation's MX capability set (`aviation.log_squawk_v1`, `aviation.add_maintenance_item_v1`, photo-commit capabilities, etc. — 10 declared capabilities) is the template to replicate for this vertical.
- **Sean's actual ask spans six distinct actors, not two:** tenant (rent + issue reporting), field technician (work-order completion), MX Director / GM (desk oversight), REIT/asset owner (portfolio rollup), prospective buyer/lessor (pre-lease walkthrough), and building inspector (formal inspection) — the last two are net-new territory that CODEX 23 never addressed at all, since it only modeled the operator/tenant relationship, not prospects or third-party inspectors.
- **The photo/video capture pipeline needs one real architecture decision before anything else gets built:** the only shipped photo-intake pattern in the codebase (aviation's squawk-photo flow) sends images inline as base64 to Anthropic vision and never persists them to Storage — it produces a text description, not a durable photo record. That's wrong for this product: buyer walkthroughs, inspector reports, and MX before/after documentation all need the actual photos/video kept, not just an AI summary. The generic Storage service (`functions/functions/lib/storage/index.js`) is the correct reuse target instead, and CODEX 27's proposed schema (Storage-URL arrays) assumed this — it just was never wired to it.
- **The current three-tier role model (`admin`/`member`/`viewer`) cannot express a GM → MX Director → Field Technician hierarchy or per-property/per-unit scoping.** CODEX 23 already named this gap eight months ago (tenant access should be scoped to a unit) and it's still unbuilt. This is real, non-trivial platform work, not a UI afterthought.

### 2.5 Photo/video capture — the one real architecture decision

Two genuinely reusable upload patterns exist, and one closely-related pattern that turns out **not** to be reusable in the way it first appears:

- **Generic Storage service — the right reuse target.** `functions/functions/lib/storage/index.js` (283 lines): a full `upload()` pipeline with MIME allowlisting (including `image/png`/`image/jpeg`), a 50MB size cap, per-tenant quota checks, access-control checks, a Firebase Storage write, a 1-hour signed URL, Firestore metadata persistence (`storageObjects/{objectId}`), and an access-log audit trail. Also has `download`/`deleteObject`/`list`/`getMetadata`. This already does everything CODEX 27's "photo persisted to Storage + Firestore metadata" principle needs — it just isn't called by anything real-estate-related yet.
- **KYC identity-photo upload — real precedent for a submit → review → accept/reject workflow.** `functions/functions/services/idVerification.js` uploads a photo ID to Storage, stores the path on a review-queue doc, and has a human-reviewer accept/reject flow (rejecting deletes the Storage object; accepting reads it back). Architecturally this is the same shape a tenant/inspector photo submission needs.
- **Aviation's squawk-photo flow — the closest workflow analog, but NOT Storage-backed, and this matters.** `functions/functions/services/mx/aircraftRecords.js` (`handleReadSquawkPhoto` / `handleCommitSquawkPhoto`) implements the exact "AI proposes from a photo, a human confirms, it becomes a record" shape this product wants — but it takes `imageBase64` directly in the request, sends it inline to Anthropic vision, and **never persists the image anywhere.** Only the resulting text description is committed (tagged `source:"photo"`); the photo itself is thrown away after the API call. CODEX 27's proposed schema (`photos_issue: string[]`, i.e., Storage URLs) assumed a Storage-backed flow — it doesn't match what aviation actually does.

**This is the one decision that needs to be made explicitly, not inherited by default:** the six actors in §3 below — especially the buyer/lessor walkthrough and the building inspector — need the actual photos and video *kept* as a durable record (a buyer needs to review images later; an inspector's report needs to attach real photos; a "before/after" MX record is meaningless without the actual images). That means the aviation ephemeral-base64 pattern is the wrong template to copy here, even though its propose→confirm capability shape is right. **Recommendation (not yet decided — see Open Decision #1 in §5): reuse the generic Storage service (`lib/storage/index.js`) for persistence, and copy aviation's two-capability propose/commit pattern for the AI-assist workflow on top of it.**

**A caveat on the Storage service that CODEX 27's schema doesn't account for:** `upload()`'s returned `downloadUrl` is a **1-hour signed URL** (it expires — see the `expires` parameter in the module), not a stable link. If a new capability naively persists that URL into CODEX 27's `photos_issue: string[]` field, every photo reference breaks an hour after upload. The fix is straightforward — persist the `objectId`/`storagePath` instead, and regenerate a fresh signed URL at read time via the module's existing lookup function — but it has to be a deliberate part of the implementation, not an assumption inherited from CODEX 27's schema as written.

### 2.6 Role/permission model — does not fit the requested hierarchy

The only enforced role vocabulary anywhere in the platform is the flat three-tier `admin > member > viewer` in `functions/functions/middleware/membershipCheck.js` (`ROLE_RANK`), read from a single `role` field on `memberships/{uid}_{tenantId}` docs. `enforceRoleGate()` only checks a rank threshold against an entire tenant — **there is no unit-, property-, or assignment-level scoping anywhere in the memberships schema.** CODEX 23 named this exact gap eight months ago (§10 of that doc calls for tenant access "scoped to a single `unit_id` at the database query layer") — it was described, never built.

**A REIT/owner → GM → MX Director → Field Technician hierarchy needs two things that don't exist today:** (1) role names beyond the hardcoded 3-entry `ROLE_RANK` map, and (2) a genuinely new scoping layer — e.g., "which properties/work-orders can this membership see" — since the current `memberships` doc carries no data-visibility scope at all, only a tenant-wide role. This is real platform work, not a per-vertical config tweak.

## 3. The Six Actors / Product Surfaces

Following the same native-app-vs-desktop split logic already in use across the platform (see `project_socii_native_app_portfolio` precedent: native investment goes to phone-camera-driven or field work; desk-based knowledge work stays responsive web):

| Actor | Surface | Why |
|---|---|---|
| **Tenant** | Native app (extend existing `TenantPortalCanvas` concept) | Rent payment + "I have an MX issue" with photo attach. Phone-first, on-the-go. Already spec'd in CODEX 23's tenant mode; today's canvas is fully mocked and needs real wiring, not a redesign. |
| **Field technician** | **New** native app, phone-camera-first | Genuinely new surface. Work-order queue, inspection checklists, before/after photo capture tied directly to a work order. Same logic as why aviation MX and DPP's QR-scan flow got native wraps. |
| **MX Director / GM** | Desktop/web (extend `PropertyManagerCanvas`) | Desk-based oversight: assigns and reviews work orders, sees submitted photos, tracks vendor dispatch. Same pattern as Dispatch/instructor/admin staying desktop elsewhere in the portfolio. |
| **REIT / asset owner** | Desktop/web, portfolio rollup | Net-new — no existing canvas or spec covers this level. Aggregates across properties/GMs; likely a reporting/analytics layer on top of the GM dashboard's data, not a new data model. |
| **Prospective buyer/lessor** | Native (phone) **and** RealWear glasses | **Net-new — not addressed by CODEX 23 at all**, which only modeled operator/tenant. Self-guided or remote walkthrough capture before any lease/purchase relationship exists — likely needs a lightweight, possibly no-account "prospect" access mode rather than a tenant-portal login, since the person isn't a tenant yet. |
| **Building inspector** | Native (phone) **and** RealWear glasses | **Also net-new.** Professional, formal inspection producing a report — same underlying capture pipeline as the buyer walkthrough, but the consumer of the output is a formal inspection document, not a purchase decision. Likely needs its own report-generation step downstream of the same photo/video capture. |

**Shared infrastructure, not shared UI:** all six actors write into the same underlying photo/video-backed property record (§2.5) — a tenant's issue photo, a field tech's before/after photo, a buyer's walkthrough footage, and an inspector's photos should all be different *entries* against the same property/unit timeline, not four separate systems. This is the "build once" principle from CODEX 27, just extended to more actors than it originally scoped.

**RealWear constraint, stated plainly:** per the existing RealWear wearables purchase (2026-09-07), the RealWear developer portal/API access is still "coming soon," not live. **The phone-camera version of the buyer-walkthrough and inspector flows is buildable now; the RealWear-glasses version is blocked on RealWear's own access opening up.** These should be scoped and shipped on separate timelines, not bundled as one deliverable.

## 4. What This Means for Sequencing

Given §2's findings, there is no version of this project that starts with the buyer-walkthrough or inspector features — those depend on the same photo pipeline the tenant and field-tech flows need first, and that pipeline doesn't exist yet in usable form for this vertical (§2.5). Recommended order:

1. **Pick one maintenance schema, redesign its photo fields, and kill the other two.** Recommend `tenants/{id}/maintenanceTickets` as the base (richest lifecycle schema), but **its `photos_issue`/`photos_resolution` fields as CODEX 27 designed them assume stable URLs, which §2.5 shows is wrong** — adopting this schema means redesigning those fields to store `objectId`/`storagePath` (resolved to a fresh signed URL at read time), not just picking the schema as-is. This redesign is part of step 1, not deferred to step 3. Deprecating the API-key-gated top-level `maintenance` collection/route and the three hardcoded canvas components' local state is bundled here for narrative flow, but **see Open Decision #8 — the API-key route specifically should not be silently killed without checking who actually holds those keys.**
2. **Declare real capabilities** in the `re.*` (or `pm.*`) namespace mirroring aviation's shape: a submit-photo capability, an AI-propose-from-photo capability, and a human-confirm/commit capability, all writing to the redesigned schema from step 1.
3. **Wire the Storage service (`lib/storage/index.js`) into that capability set** — this replaces the aviation ephemeral-base64 pattern with real persistence, per §2.5. (The signed-URL fix itself is scoped in step 1, since it's a schema property, not a wiring detail.)
4. **Reconnect the three existing canvases** to the real capabilities/schema — this alone fixes the dead "Submit"/"Pay Now" buttons and turns CODEX 23's already-designed UI into something real, before any new UI is built.
5. **Only then** build the net-new surfaces: field-technician native app, buyer/lessor walkthrough capture, building-inspector capture, and the REIT portfolio rollup — all of which consume the same pipeline built in steps 1-3. **Before any of these ship, resolve Open Decision #9 (tenant privacy / entry-notice / consent) — capturing photo or video inside an occupied unit without a compliance framework is a real legal exposure for a platform whose whole positioning is compliance-aware for regulated verticals.**
6. **Role/scoping work (§2.6) is shared platform infrastructure, not a vertical-scoped change — treat it as its own workstream, not a parallel task inside this one.** `ROLE_RANK` and `membershipCheck.js` gate every vertical on the platform (aviation, DPP, MSR, everything), not just real estate. Extending it to support property/unit-level scoping needs sign-off from whoever owns those other verticals, since a regression here surfaces as a bug somewhere else entirely. It must land before the GM/MX-Director/Field-Tech hierarchy is real — right now anyone with `member` role sees everything in the tenant — but "in parallel" should mean "tracked as a coordinated dependency," not "quietly done alongside."

## 6. Tenant Privacy, Right-of-Entry & Recording-Consent Framework (Open Decision #9)

**This is an engineering-facing compliance framework — what the product needs to capture, gate, and disclose — not a legal opinion.** Real counsel review is still required before any occupied-unit capture flow (MX, buyer/lessor walkthrough, building inspection) ships, the same way AV-032's rules require real FAA-approved documents rather than platform reference material. Two genuinely distinct legal questions live here; conflating them was the gap in the original Open Decision #9.

### 6.1 Right of entry (applies to any real, physical entry — MX, inspection, buyer walkthrough)

Notice requirements are set state-by-state, and sometimes further restricted by city ordinance or the lease itself (which can be *more* protective than the state floor, never less):

- **24 hours** is the most common fixed period (~16 states, including California, Nevada, Oregon, Colorado, Virginia).
- **48 hours** in several states, including **Hawaii**, Washington, and Arizona — directly relevant given LFN/Hawaii is already a live thread in other work this session.
- **"Reasonable notice"** with no fixed hour minimum in several states (Texas, New York, Illinois statewide, Wisconsin, Maryland, Pennsylvania) — vaguer, and arguably needs a conservative internal default (e.g., defaulting to 24 hours) rather than treating "reasonable" as "none."
- **Florida** requires only 12 hours — a real outlier worth not assuming matches the 24-hour default.
- **16 states have no statutory notice period at all** — the lease terms and general reasonableness standards govern instead.
- **Emergency entry needs no notice anywhere** — this is the one universal exception.

**Engineering requirement:** every ticket/inspection/walkthrough that involves physically entering an occupied unit needs a `noticeGivenAt` timestamp, a `noticeMethod` (posted/emailed/texted/verbal), and jurisdiction-aware minimum-notice validation before it can move to a "field tech dispatched" (or equivalent) status for a non-emergency case. An emergency-flagged ticket bypasses the notice gate but should log *why* it was flagged emergency — an audit-trail requirement, consistent with this platform's append-only-event philosophy elsewhere (aircraft logbook, squawks). Jurisdiction should plug into the **existing** RAAS jurisdiction folders (`raas/real-estate/CA/FL/TX`, per §2.2's audit) rather than a new config surface.

### 6.2 Recording consent — video and audio are legally different, and this doc's original framing didn't separate them

- **Audio is the real legal risk.** As of this research, **12 states require all-party consent** for recording a conversation: California, Connecticut, Delaware, Florida, Illinois, Maryland, Massachusetts, Montana, New Hampshire, Oregon, Pennsylvania, Washington. Recording audio inside an occupied unit without the tenant's (and anyone else present's) consent can be a **criminal** wiretap violation in these states — Maryland and Massachusetts specifically carry penalties up to five years. The other 38 states + DC are one-party consent (the recording party's own consent is sufficient).
- **Video alone is a different legal question.** Wiretap/eavesdropping consent statutes specifically target *audio* interception — silent video capture doesn't trigger them. Video in a private residence is instead governed by general privacy-tort principles (reasonable expectation of privacy), and for a lawfully-present party (proper right-of-entry notice given, per §6.1), documenting a unit's condition is generally permissible — but should still avoid unnecessary capture in bathrooms/bedrooms and never capture a person's identity without separate, explicit consent.
- **Engineering requirement:** default all MX/inspection/walkthrough capture to **video/photo only, audio muted**, regardless of state. Only unlock audio behind an affirmative, logged, timestamped consent flag ("who consented, when") — required unconditionally in the 12 all-party states, and good practice to require everywhere rather than branching default behavior by jurisdiction for something this consequential.
- **Risk is not evenly distributed across the three actor types.** A tenant photographing *their own* reported issue is the lowest-risk case (self-consent is trivially satisfied). A field technician documenting before/after work is a known party the tenant is expecting, per §6.1's notice. **The buyer/lessor walkthrough is the highest-risk flow** — a third party, potentially previously unknown to the current occupant, entering and recording inside someone else's currently-occupied home — meaning §6.1's notice *and* §6.2's consent framework both matter most acutely for that flow specifically, on top of the access-token security review already required by Open Decision #4's resolution.

### 6.3 What this framework does not resolve

City/county ordinances that exceed state minimums, lease-specific terms, HOA rules, and any state-specific nuance beyond the top-line figures above are all real gaps this pass didn't (and can't responsibly) resolve — that's real counsel's job, not a research pass. Treat §6.1/§6.2 as the floor the engineering needs to support, not the ceiling of what real compliance requires.
