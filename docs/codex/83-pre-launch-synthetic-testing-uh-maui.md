## 0. The three real goals, and how each maps to what's already built

1. **Find bugs before UH Maui does.** Directly motivated by this session's own CODEX 82 finding — the CET sign form was provably unreachable through any chat flow until today, and nobody would have found that without deliberately trying to reach it. More bugs like that almost certainly exist.
2. **Estimate real per-student data usage** for the pricing conversation already in progress (semester usage review, per the corrected Order Form). Directly usable: `recordInteraction()`/`computeTenantUsage()` (`services/billing/boxPlanUsage.js`, wired further into evaluation-signing by CODEX 82) already produce a real per-tenant/month number — synthetic traffic through an isolated test tenant would exercise the exact same counters real traffic will.
3. **Seed Grace's content-gap QC loop** (CODEX 81's `[[CONTENT_GAP:...]]` → `supportContentGaps`) before real faculty/students hit real gaps, so her Locker is already stronger on day one.

All three are legitimate, and (2) and (3) genuinely reuse infrastructure already built this session rather than requiring new pipelines. But **goal 1's actual test coverage — trying escalation-triggering and distress-flavored phrasing on purpose, which is exactly the kind of edge case "thousands of variations" is supposed to surface — collides directly with a real, currently-unconditional alerting system.** That collision is §1, and it has to be resolved before any volume testing starts.

**Round-3 caveat, load-bearing — goals 2 and 3 quietly narrow once §3's correction is taken seriously.** UH Maui's per-seat pricing and Grace's real support load are both about *student* traffic. §3 establishes that Hannah is instructor-facing today, not student-facing — so Phase 0 testing (§3, §7) produces a real usage number and real content-gap signal, but for the wrong population: department-chair-style operational questions, not a class of students doing nightly Socratic review. **Any usage estimate or content-gap signal that comes out of Phase 0 must be labeled provisional, population-mismatched, and superseded once Phase 1 (Hannah's actual student mode) ships** — not treated as a preview of real per-student volume. This is a caveat on the output, not a reason not to run Phase 0.

**Round-2 finding, fully audited round 3 — reuse an existing exemption pattern instead of inventing one.** Round 2 flagged that `demo-`-prefixed tenants get exempted from `checkSafetyContactGate` and `isSupportSubsidized`'s credit deduction, citing "six call sites" without confirming all of them were checked — a fair thing to press on, since repurposing an existing prefix for QA isolation means inheriting *everything* gated on it, not just the two behaviors this CODEX wants. **Round 3 enumerated and read every actual call site** (there are exactly five, not six):

## 2. No existing sandbox/test-tenant isolation pattern — reuse the `demo-` convention, don't invent a new one

Grepped for "sandbox"/"test-tenant"/"qa-tenant" across the backend: "sandbox" in this codebase already means something else entirely — the worker-building/developer-preview surface (`services/sandbox/tenantLocker.js`, `services/sandbox/liveEscalation.js`), unrelated to QA isolation.

**Fix required:** name the designated test tenant with a `demo-` prefix (e.g. `demo-sociii-qa`) to inherit the existing safetyContact and subsidized-credit exemptions for free (§1, round 2/3 — fully audited, safe) — then explicitly verify (not assume) whether `sendBoxPlanUsageReports()` (CODEX 76) and `computeTenantUsage()`'s tenant-selection logic already skip `demo-`-prefixed tenants the same way, or whether that still needs an explicit exclusion so synthetic usage numbers never get emailed to a real institution as if they were real. Internal review of the synthetic usage number happens directly against `boxPlanUsage/{demo-sociii-qa}_{monthKey}`, not through the customer-facing report path.

**Round-3 finding — ownership of the tenant's lifecycle, not just its creation, is undecided.** A permanent QA tenant accumulating months of synthetic conversation history and content-gap entries is a different maintenance shape than a one-time test run — nobody currently owns deciding whether `demo-sociii-qa` persists indefinitely or gets periodically reset. **Decide this explicitly before first use, not after it's accumulated enough history to make either choice annoying.**

**Round-4 correction — the round-3 reset default was wrong, and worked against §6's own point.** Wiping `supportContentGaps` entries on every pass destroys the *cross-pass* frequency signal `gapHash` (CODEX 81) exists specifically to surface — a gap that shows up in every single test run for a month is a much stronger signal than any one run alone, and resetting per-pass would flatten that into N indistinguishable single-occurrence entries. **Corrected default: reset conversation history only** (genuinely pass-specific, shouldn't accumulate) — **`supportContentGaps` entries persist across passes**, stay tagged `synthetic-test`, and are reviewed per-pass per §6's cadence without being wiped. The per-pass review (§6) and the reset policy (§2) need to work together, not against each other.

**Round-4 addition — clean-stop behavior when the §5 cost/exchange cap trips.** Not previously specified. When the harness's hard cap fires mid-pass: stop issuing new persona turns immediately; treat whatever synthetic data was generated up to that point as a valid, usable partial result for that pass (don't discard it); the pass's conversation history still gets the normal per-pass reset described above before the next pass starts, so a cap-triggered stop needs no special-case cleanup beyond that.

## 5. No existing scripted conversation harness — genuinely net-new

`functions/functions/monitoring/workerCanary.js` was checked as a candidate reusable pattern — it's a metadata/rules-integrity health check (canvas spec validity, ruleset load success), not a conversation simulator, and doesn't call `/v1/chat:message` repeatedly. **Nothing in this codebase today provides a template for scripted synthetic conversations.** This is real, net-new build work, not a wiring gap.

**Recommended shape — two tracks, not one, matching Sean's own instinct that Chrome matters:**
- **Track A — high-volume, API-level.** Programmatic calls directly against `/v1/chat:message` (and `/v1/edu:evaluation:sign` for the eval tool), driven by synthetic "student" and "instructor" personas with varied question types, confusion levels, and (once §1 is fixed and verified) escalation-edge-case phrasing. This is the right tool for volume — hundreds to low thousands of exchanges, cheap and fast, and the right mechanism for goals 2 (usage) and 3 (content-gap seeding). The Workflow tool's `agent()` primitive is a natural fit for orchestrating many parallel synthetic personas at this layer.

  **Round-2 addition — actual cost estimate, absent from the first draft.** Worker chat runs on `claude-sonnet-4-6` (`index.js:360`, $3/M input, $15/M output). A typical multi-turn exchange (~800-1,500 input tokens including system prompt/history, ~300-500 output) runs roughly **$0.01-0.03 per exchange**, rising somewhat as a session's own history grows across turns. "Hundreds to low thousands of exchanges" is therefore plausibly **$50-300 in raw inference cost** — genuinely cheap, but it should be a stated number going into this, not an unstated assumption.

  **Round-3 finding — an estimate is not a cap.** A harness bug (a persona that never terminates, a retry storm) could blow past the $50-300 estimate by an order of magnitude before anyone notices, especially unattended. **The harness itself must enforce a hard stop — a max exchange count AND a max spend — not just target a number in this planning doc.** Build this in from the start, same as §6's synthetic-gap tagging.
- **Track B — smaller-volume, real Claude-in-Chrome browser sessions.** Sean's point stands: Chrome is the actual environment real students and faculty will use, and Track A structurally cannot catch UI/rendering bugs — it would never have found today's "the sign form is unreachable" bug, since that bug lived entirely in canvas-signal wiring, not in what any worker said. Reserve real browser automation for a curated set of realistic end-to-end flows (sign an evaluation, ask Hannah a tutoring question, ask Grace an access question, trigger a deliberate escalation once §1 is safe) rather than "thousands of variations" — dozens of real browser walkthroughs, not thousands, is the right scale for this track.

  **Round-3 finding — "once §1 is fixed and verified" needs a definition, per this project's own hard-won standard.** The safetyContact gate took five red-team rounds partly because "the code exists" and "it actually works" got conflated more than once. **"Verified" here means: a real test call to the patched `/v1/support:escalate` route confirms no email/SMS actually fires for a `demo-`-prefixed tenant** — not just a code read confirming the patch was applied. Do this check before Track B ever runs, the same way CODEX 82's own deploy checklist required a real post-deploy probe, not just a clean `git diff`.
- **Track C — mobile, deferred.** Sean separately noted the mobile app matters too "if we can get an app up and running." CODEX 57 (mobile Capacitor app store build) is the relevant prerequisite — no point scoping mobile browser/app testing before that app exists. Named here so it isn't forgotten, not scoped further.

## 6. Grace's content-gap seeding needs a synthetic/real distinction

Synthetic traffic will produce real `[[CONTENT_GAP:...]]` entries in the same `supportContentGaps` collection Ruthie reviews weekly (CODEX 81's named default). Mixing synthetic and real signal in her actual review queue risks either wasting her time on synthetic artifacts or — worse — training a habit of skimming past entries that turn out to matter.

**Fix required:** tag synthetic-sourced gap entries distinctly (e.g. `source: "synthetic-test"` on the write) and exclude them from Ruthie's regular review by default.

**Round-3 finding — this document was about to reintroduce the exact unowned-log problem CODEX 81 already found and fixed once.** CODEX 81 hit this failure mode with `alertFeed/platform-ops` and fixed it by naming a default reviewer and cadence rather than leaving "someone should look at this" open. The first draft of this section said "Sean/whoever runs the testing pass reviews the synthetic gaps directly" with no cadence — same gap, reintroduced. **Named default:** since testing runs are discrete events, not continuous production traffic, review is event-triggered, not calendar-based — **Sean (or whoever runs a given Track A pass) reviews that run's synthetic `supportContentGaps` entries before promoting anything into the real content-update process, and before considering that run's results final.** Not a standing weekly commitment like Ruthie's real queue — tied to each test run itself.
