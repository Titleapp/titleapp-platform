## The finding that grounds this doc

While scoping Dev, re-read `docs/codex/97-worker-team-architecture-robustness-comms-and-reporting.md` for the first time since it was written — the doc that, the *previous* night, already decided the persona-email-alias approach and specified a red-teamed gating sequence for going live with it (rate limiter, code-enforced AI-disclosure footer, correction-protocol auto-suspend, task-canary-passing, in that order, before an inbound listener goes live).

The Gmail persona-reply pipeline built the same night as this doc (webhook, moderation gate, send/approve flow) was built **without re-reading CODEX 97 first**, and skips past that gating sequence — none of the four safeguards exist yet. Nothing went live (the activation step, `gmail:startPersonaWatch`, was never called), so no actual harm occurred — but the code was fully built and one function call away from running live, autonomously, in production, in a state its own prior design doc had explicitly red-teamed and gated against. See [[project_gmail_persona_reply_pipeline]] for the full detail; flagged and corrected in memory the same session this was found.

**This is precisely a "config/process drift" and "permission drift" case from Sean's own CODEX** — a capability operating (or about to operate) outside the tier its own governing spec assigned it. A human (me, that night) missed it because the relevant context was sitting in a doc, not something re-checked before building.

**Red-team correction (2026-09-22, same session):** the first draft of this doc put that check inside Dev — which only runs *after* activation, on Dev's next scheduled pass. That's detection, not prevention: between an activation and Dev's next run, a bad activation would already be running live and unmoderated, which is exactly the harm CODEX 97 red-teamed against. **Fixed the same session, before this doc was even finalized:** the gate now lives in code, inside the activation function itself (`watchMailbox()` in `services/social/gmail.js`), via a new machine-readable registry (`config/capabilityGates.js`) — `assertGatesPass('persona-email-inbound-listener')` runs first and throws if any registered gate doesn't pass. **The red-team review also caught that the Cloud Scheduler renewal job was a second, ungated activation path calling the same underlying function** — confirmed true, the job was paused immediately and the gate placed in the one shared function both paths call, closing both at once. Verified live: both `/v1/admin/gmail/renew-watch` and the `gmail:startPersonaWatch` route now fail closed with a clear error listing every unmet gate.

**Dev's role on this specific check is now the backup, not the primary control** — verifying the code-level gate/registry itself hasn't been bypassed, removed, or silently made to pass, not the thing standing between "gate documented" and "gate enforced." That distinction generalizes: **any future gated capability must have its gate implemented in `capabilityGates.js` and asserted inside the activation function itself**, with a CI/lint rule (not yet built) that fails the build if a new gated-capability activation path doesn't reference a registered gate — so forgetting is caught at deploy time, not discovered later by Dev or, worse, not discovered at all.

## What already exists — build on it, don't replace it

`functions/functions/monitoring/workerCanary.js` (+ `chatCanary.js`, `qualityCanary.js`) is real, live, already-running synthetic health-check infrastructure:
- A single findings shape: `{ scope, id, severity ("red"|"warn"), reason }`.
- One health doc (`HEALTH_DOC`) holding current status + reds + warns, one `workerHealthEvents` history collection.
- De-duplicated alerting: fires on a *new* red, re-pings if still red after 12h, announces recovery — not a fresh alert on every run.
- Existing checks: rules-loading health, worker-catalog/canvas-spec health.

**Dev is not a new monitoring system. Dev is this system, extended with new checks and a worker identity/voice on top of it**, so it can take a turn in the staff meeting and own ledger commitments like Sean's CODEX describes, instead of just being a silent cron job.

## Dev's v1 checks (concrete, ordered by how immediately valuable they are)

Each check below has a **defined expected state**, not just a pass/fail — per red-team feedback, "no watch because not activated" (fine), "watch expired" (bad), and "watch exists but shouldn't per the gate registry" (red, and the more serious case) must be distinguishable, or they collapse into the same undifferentiated signal.

1. **Gate-registry integrity check** (revised from the original "gated-capability activation" idea, which has now moved into code — see above). Dev's job here is narrower and mechanical: confirm `capabilityGates.js`'s registered predicates still exist, still return real fail-closed results (not a stubbed `true`), and that the live Gmail watch state matches what the registry currently allows. Deterministic code against a deterministic registry — no LLM judgment involved, per the point below.
2. **Gmail watch health.** `gmail.users.watch()`'s returned `expiration` — checks it's still comfortably in the future *when a watch is expected to exist per the gate registry*, distinct from "no watch, correctly, because gates aren't met" (not a finding) and "watch exists despite gates failing" (red — the registry was bypassed). Cross-check: Pub/Sub subscription `gmail-persona-email-push-sub` for a growing undelivered/dead-letter count.
3. **Pending moderation-queue age.** Any `pendingPersonaEmailApprovals` doc older than a threshold (24h) unresolved — warn; red past 48h. **Fail-safe: CLOSED 2026-09-23.** Was correctly re-flagged by a second red-team pass as a hard blocker before activation, not a "decide later" item, given a red alert could sit unactioned for 12+ days across a real flying rotation. The safe default itself (a stale draft **expires unsent**, never auto-sends on timeout) needed no judgment call from Sean, so it shipped: `exports.personaEmailApprovalExpirySweep`, every 6h, expires anything pending past 48h with `expiredReason` logged. **Backup-approver identity: still OPEN, not closed by the above.** A real role/access decision remains genuinely undecided — the fail-safe above closes the worse failure mode (silent indefinite limbo, or an accidental auto-send) while that decision is pending; it does not resolve it. Splitting these two explicitly per round-4 red-team feedback: a single "CLOSED" label on this bullet read as fully resolved when a load-bearing piece wasn't.

3a. **Expiry-sweep heartbeat.** Added round 4: the sweep above is now a safety-critical fail-safe, not a convenience function, so it gets the same "silence must not read as green" treatment check #7 applies to Dev itself. `expireStalePersonaEmailApprovals()` writes `config/personaEmailExpirySweepHealth` (`lastRunAtMs`, `lastExpiredCount`) on every run, even when nothing expired; Dev's `checkExpirySweepHeartbeat()` reds if that heartbeat is stale past 8h (6h schedule + 2h slack).
4. **Config/dependency existence — moved to deploy-time validation, not a Dev check.** Per red-team feedback, a hand-maintained list (like `CROSSMINT_COLLECTION_ID_BASE`) goes stale by construction. The real fix is the service validating its own required config at startup and failing fast; Dev's role shrinks to *reporting* what that startup validation already caught, not independently re-deriving the list.
5. **Existing worker-canary findings, surfaced through Dev.** Not new checks — visibility into `workerCanary.js`'s current red/warn state in one place. **Alert-path consolidation needed:** this and Dev's own findings must share one de-duplication layer with the existing SMS/email `sendAlerts`, or the same incident pages Sean twice.
6. **Permission drift** — deferred, depends on the permission-enforcement build per CODEX 97.
7. **Watching Dev itself.** `workerCanary.js` gets a new check: alert if Dev hasn't reported within its expected interval. Dev cannot be the only thing checking Dev's own health — silence must not read as green.

## Access Dev needs, and the boundary it doesn't cross

**"Read-only" must be an IAM fact, not a convention — red-team correction.** If Dev runs under the default Cloud Function service account (as everything else in this deployment currently does), it likely has Editor and the Admin SDK bypasses Firestore security rules regardless — meaning "Dev is read-only" would be true by agreement only, not enforced. **Hard requirement before Dev ships, not a nice-to-have:** Dev runs under its own dedicated service account, granted only `roles/datastore.viewer`, `roles/logging.viewer`, `roles/monitoring.viewer`, and Pub/Sub viewer — nothing else. This is the thing that makes the "read-only" claim actually true.

- **Firestore, metadata only — INTENDED, not yet enforced — corrected 2026-09-23, second red-team pass.** The prior version of this doc stated this in present tense as though it were the current state; it isn't. `roles/datastore.viewer` (granted 2026-09-23) reads whole documents, bodies included — Firestore has no field- or collection-level IAM restriction, so there is no native way to grant "metadata only." **This is a live exposure today, not a future design gap**: Dev's actual IAM grant can read real student records or borrower financial data in `digitalWorkers`, `pendingPersonaEmailApprovals`, `personaEmailReplyLog`, `workerHealthEvents`, and DTC/chain-anchor docs, even though no code path currently asks it to. What's actually true right now: Dev's own code only ever reads `config/devHealth`, `config/gmailPersonaWatchState`, `pendingPersonaEmailApprovals` (status/createdAt only, never message content), `config/personaEmailExpirySweepHealth` (metadata only), and `config/workerHealth` — metadata-only is enforced by code discipline today, not by IAM. A careless future check reading message content from a sensitive collection would compile, deploy, and work, with nothing at the IAM layer to stop it. **Round-4 fix — a backstop for the discipline, not the IAM fix itself:** `scripts/lint-dev-worker-scope.js`, wired into `firebase.json`'s functions `predeploy` alongside the existing gate lints, fails the build if `devWorker.js` references `draftText`/`inboundBody`/`sendArgs`/`rawMessage`/`personaEmailReplyLog` — the same class of grep-based CI backstop `lint-gmail-watch-callsites.js` already provides for a different boundary. This closes "nothing catches it at deploy time," not "IAM can't technically be bypassed" — the real fix (a separate metadata-only datastore, or a narrow internal read endpoint) remains unbuilt — see Still Open.
- **GCP, read-only:** Cloud Logging Viewer, Cloud Monitoring viewer, Pub/Sub viewer. **Billing note:** cost-anomaly detection is not real-time unless billing export to BigQuery is set up — plan for roughly a day of lag, don't design a check that assumes same-day cost data.
- **Explicitly not:** Google Workspace admin access of any kind, ability to modify OAuth tokens, ability to change any account setting or capability tier directly, its own broad service account. Per Sean's own CODEX ("Dev starts read-only... a human approves any change").

## Interface for v1 — don't wait on the shared-meeting infrastructure

The hardest piece of Sean's full staff-meeting concept (a live, shared, turn-taking multi-worker session) doesn't exist yet and is its own build. Dev's v1 value shouldn't be blocked on it:
- Findings write to a `devFindings` collection, same shape as `workerCanary.js`'s findings (`scope`, `id`, `severity`, `reason`, plus `proposedFix` per Sean's "diagnoses and proposes fixes").
- Real-time notification for anything red reuses the exact SendGrid-notify pattern already built for the moderation-gate approval emails the same night — no new send mechanism needed.
- Once the shared-meeting surface exists, Dev's "turn" reads from the same collection instead of a separate report — this interface is meeting-agnostic on purpose.

## Registration as a real worker

Per the existing `digitalWorkers` Firestore + `useWorkerCatalog.js` normalization pattern, Dev needs a real catalog entry (`display_name`, `capabilitySummary`, a `canvasSpec` if it should render in the UI like other workers) so it isn't a headless cron job pretending to be a persona — it should show up the same way Ivy/Max/Jordan do. Persona email identity (a `dev@sociii.ai` alias) is not urgent for v1 — Dev's primary interface is findings + the eventual meeting, not an inbox — but worth reserving in `personaEmailIdentities.js` for consistency once it's built.

## Dev is deterministic code narrating findings — not an LLM judging them

**Red-team correction, important:** Sean's original CODEX described Dev as both a cron-job extension and a "worker persona with a voice that proposes fixes." Those need to be split cleanly. If an LLM generates `proposedFix` freely from log/queue contents, and those contents can include inbound email text (untrusted, per CODEX 97's own risk register #2), that's a prompt-injection path aimed straight at Sean's own approval step — the exact class of risk this whole doc exists to prevent, reintroduced through the back door. **Every check is deterministic code with a defined pass/fail condition.** A persona layer may narrate findings in Dev's voice for the eventual staff meeting, but proposed fixes are templated per check type, selected from a fixed set, never freely generated from data content.

## Explicit non-goals for v1

- No write access to anything, and no broad service account — its own viewer-only identity, not the shared default.
- No permission-drift checking yet (blocked on the enforcement build, not a v1 cut).
- No new alerting channel — reuse and de-duplicate against what exists (`workerCanary.js`'s `sendAlerts`), not a second parallel path.
- No LLM-generated fixes or judgments — checks and remediation templates are both fixed code.

## Legal note, flagged not resolved here

The AI-disclosure footer (CODEX 97, resolved "yes" 2026-09-21) may not be optional best-practice — the EU AI Act's transparency obligations for AI systems interacting with people are understood to have started applying August 2026, which is directly relevant given the Estonia entity and EU DPP work already in flight. Worth a real check with counsel before any persona sends externally under its own name — noted here so it doesn't get lost, not resolved in this doc.
