## 4. AEO/GEO — external memo content (unverified against this repo, flagging clearly)

The following is relayed from an external memo (*AEO/GEO as a Horizontal IVY Capability*, written against the Hardgrave/Garris pilot) — treat as a real, well-reasoned strategic thesis, but note it has NOT been checked against this codebase the way §1-3 above have been. Before acting on any of it, verify current Ivy prompt/capability structure directly.

**The thesis:** search is splitting into two layers most businesses don't optimize for — AEO (winning Google's zero-click answer formats: featured snippets, People Also Ask, AI Overviews) and GEO (getting cited inside AI chat tools like ChatGPT/Perplexity/Gemini/Claude that synthesize answers from multiple sources). Adoption is still thin industry-wide — the memo compares the opportunity window to early-2000s SEO, where the edge goes to whoever moves first and decays as competitors catch up.

**Why it's an Ivy problem, not a one-client problem:** every SOCIII vertical depends on being *found* by someone doing a discovery/evaluation search — a referral partner, a prospective customer, an evaluator. If this capability is built once, generically, it's a horizontal SOCIII product line; if it's built as a one-off for a single client, it's a favor bundled into a deal, not a differentiator.

**What Ivy would need to be able to do, per the memo:**
- Structured, answer-first content generation (FAQ-schema pages, topic clusters) targeting the specific questions a referral partner/evaluator would ask an AI tool
- Entity-consistency enforcement — the same credentials/facts about a client repeated identically everywhere crawlable
- Schema/markup automation (FAQPage, structured data, freshness/dateModified discipline)
- Citation monitoring — tracking whether/how often a client actually shows up in AI Overviews, ChatGPT, Perplexity, Gemini answers for target queries, as the real KPI (not traffic/rank)
- Review/profile hygiene (GBP completeness, review velocity) as a trust-signal input

**Architecture constraint flagged by the memo, worth taking seriously:** whatever Ivy produces per client should land as an integrated layer on the client's *existing* domain, never a separate/parallel site — a second domain splits authority and creates entity ambiguity, actively undermining what AEO/GEO rewards. This has a real implication: Ivy's delivery model becomes "generate and place content/schema into an existing site/CMS," which likely means Ivy needs write access into a client's CMS or hosting — a genuine architecture question, not a content question. **Open question, not yet answered:** does Ivy's current architecture support this, or does it currently assume greenfield builds? Needs a direct code check before scoping further.

**Sequencing per the memo (agree with this):** build and validate against the Attorneys Title pilot first, instrumented with citation-frequency and referral-attributed-lead KPIs — resist generalizing into a templated cross-vertical product until the pilot shows real signal. This matches the same discipline already applied elsewhere in this codebase (don't build the horizontal version before the vertical proof exists).

### The pitch — how to walk Chad and Troy through this

Most small-business owners, including sharp ones, have not internalized that referral-and-evaluation searches are shifting from "google it and click a link" to "ask ChatGPT/Perplexity/Google's AI Overview and get a synthesized answer with no click at all." The most persuasive way to teach this is to show it, not describe it:

1. **Live demonstration, ideally on the actual onboarding call — with a real execution risk flagged after a second round of red-team review.** AI answer engines are non-deterministic and drift over time; a live re-query in the room might not match the recorded Phase 0 baseline — it could cite Attorneys Title unexpectedly, return something anticlimactic, or (worse) give a named competitor a glowing answer live in front of Chad and Troy, with no recovery in the moment. **Treat the recorded Phase 0 baseline as the primary artifact ("here's what we found") and any live query as an optional bonus, not something the pitch's credibility depends on.** If a live query is run anyway, use generic phrasing ("a competing title company," not naming one) — reserve actually-named-competitor queries for the private baseline research, never a live query in front of the client. Example question shapes for the baseline research: "best title company near Athens TX," "how fast can a title company close a cash sale in Henderson County," "does \[named competitor\] offer RON closings in Texas." Show what currently comes back: likely either silence on Attorneys Title specifically, or a competitor getting cited by default because nobody in the local market has structured their content for this yet.
2. **Name the stakes in their own terms:** the referral partners who used to ask a colleague "who's a good title company" are increasingly asking an AI tool instead, and whoever's content is structured to be *the answer* wins that referral before a human ever visits a website. This is not a hypothetical trend — it's already happening, and adoption among title companies specifically is close to zero right now, which is exactly why moving first matters.
3. **Set the expectation correctly:** this is not a website redesign project and not a paid-ads project — it's a content-and-structure project layered onto what they already have, instrumented with a real, checkable metric (citation frequency) rather than vague "more traffic" promises.
