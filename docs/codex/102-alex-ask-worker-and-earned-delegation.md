# CODEX 102 — Alex's `ask_worker` Capability, and Earned Delegation Rights

**Status:** Scoped 2026-09-23, revised same night after a red-team pass caught real design gaps before anything was built — the cheap moment to fix them. Not yet built. Sean approved v1 for build; the redesign below is what should actually get built, not the first draft.

**Sean, 2026-09-23**, on the "staff meeting" discussion: workers stay siloed from each other — that isolation is a deliberate security boundary (CODEX-S52.65), not something to remove. The one exception: Alex should be able to reach into any worker's silo on request, audited, not a live multi-agent meeting. Separately, on delegation generally: *"It seems like there should be some method of earning the trust of the platform before you can delegate to others. Otherwise we might end up with the lazy bossy coworker syndrome."*

---

## Red-team pass (2026-09-23, before any code exists)

The first draft undersold what `ask_worker` actually does. Caught before building, not after:

1. **"Audited" implies contained; it isn't.** `ask_worker`'s mechanism means Alex's effective data access becomes the union of every worker's data access, gated only by a rate limit and after-the-fact logging — both throttle/detect controls, not access-boundary controls. This doesn't remove the silo boundary Sean wants kept, but it does bridge across every silo at once, controlled by nothing but Alex's own judgment about what to ask. Named explicitly below rather than left implicit in "audited."
2. **Does it only return an answer, or can it trigger actions?** The first draft didn't say. If `ask_worker` runs the target worker's *full* response-generation path including its normal tool-calling, Alex asking Max a question could cause Max to *act* — draft something, update a record, clear a queue — not just answer. That's a materially bigger deal than a visibility question. **Resolved below: `ask_worker` is answer-only, structurally, not by convention.**
3. **"Sean-initiated only" was a stated intent, not an enforced fact** — the exact pattern CODEX 100 found wasn't real until it was an IAM grant. Fixed below by construction, not by a gate predicate promising to check caller context.
4. **Indirect injection.** If Sean pastes forwarded content or a document into his message to Alex, and the trigger condition for `ask_worker` is just "reachable from Sean's message," attacker-controlled content could get Alex asking questions Sean never intended — same class of risk CODEX 97's risk register already names for inbound email. Not solvable by architecture alone; named as an accepted, open risk below, not claimed as solved.
5. **Rate-limiter reuse was ambiguous** — same bucket or same pattern, global or per-target-worker. Resolved below: separate bucket, global scope.
6. **No aggregate view of usage** — ironic, given the capability exists specifically to prevent Alex over-relying on asking instead of reasoning, and there was no way to actually see that pattern forming. Added below.
7. **"Registered in `capabilityGates.js`" without a stated predicate.** If the only real condition is "rate limit not exceeded," that's the rate limiter doing its job, not a distinct capability gate — pretending otherwise overstates the governance. Corrected below to be honest about what v1 actually gates on.
8. **`ask_worker` as a future delegation shortcut.** Not a flaw in the design, a risk to the design holding — a future session under time pressure could reuse `ask_worker`'s transport as an informal stand-in for real delegation once it exists, since delegation is deliberately harder to get. Named explicitly below as a one-line guardrail.
9. **Part 2 (delegation) gaps**, all still-deferred since Part 2 isn't being built now, captured for whenever it is: the reliability metric is gameable if commitment difficulty isn't normalized and "a commitment" isn't defined consistently across worker types; the doc didn't say whether the gate is checked once (earned, then cached) or continuously (CODEX 100's own round-2 lesson: continuous, not just at activation); and nothing guarantees a single enforcement path, the same shape of gap CODEX 100 found with the Gmail Cloud Scheduler job.

## Part 1 — `ask_worker`, redesigned

**What it is:** a tool Alex can call mid-conversation — `ask_worker(workerSlug, question)` — that gets a real, grounded answer from that worker's own knowledge/rules/data, for Alex to relay or synthesize into its reply to Sean.

**What it explicitly is not, now enforced by construction, not just stated:**

1. **Answer-only, structurally.** The underlying call `ask_worker` makes runs the target worker's response-generation path in a mode with **no side-effecting tools available** — whatever normally lets that worker draft, send, update a record, or clear a queue is not present in this call. It can read and reason with that worker's grounding; it cannot cause that worker to act. This is the single most important correction from the red-team pass — without it, "Alex asks a question" and "Alex triggers an action in another worker's name" are the same code path, and they must not be.
2. **No separate entry point — closes the CODEX 100 dual-path class of bug before it can happen.** `ask_worker` is never its own HTTP route and never independently callable. It exists only as a tool binding inside Alex's own `/chat:message` request handler — reachable only while a real, authenticated turn from Sean's own session is actively being processed. There is no second path (no scheduled job, no other worker's turn, no admin route) that can reach it, because there is nothing else to call. This is what actually makes "Sean-initiated only, not autonomous" true, rather than a description of what nothing else happens to call yet.
3. **Visible, not a backchannel.** The question and answer get logged into the target worker's own chat history, tagged as invoked by Alex on Sean's behalf. If Sean opens Max directly later, he sees the exchange.
4. **Bounded, and now concretely specified.** A dedicated rate-limit bucket — `alexAskWorkerBudget`, its own Firestore doc, not sharing state with `personaSendRateLimiter.js` (same pattern, separate instance, so a burst of persona-email sends can't eat into or be eaten by this budget). **Global across all target workers** (10/hour total, tune after real usage), not per-target-worker — per-worker would let Alex spread 10/hour × N workers, defeating the actual goal (stop "go ask someone" substituting for Alex's own reasoning), not just cap total volume.
5. **The gate, honestly specified.** `ask_worker` does not get a separate `capabilityGates.js` registration pretending to check something beyond the rate limiter — that would overstate the governance for no real benefit. Its one real, enforced condition is the rate-limit budget above, checked transactionally before the call proceeds, fail-closed. If a genuinely separate condition is ever needed (e.g., "don't ask a worker that's itself suspended"), that's a new, named, justified gate — not implied by registering in the same file other gates happen to live in.
6. **A visible rollup of usage.** `alexAskWorkerBudget`'s doc (or a small `alexAskWorkerLog` alongside it) is readable by Dev, extending Dev's existing pattern (`workerCanary.js`'s "Dev cannot be the only thing checking Dev" logic) so a volume spike or a suspicious cross-silo fishing pattern is actually detectable in one place, not only by Sean happening to notice a pattern across several workers' individual histories.
7. **Indirect injection — named as an accepted, unresolved risk, not claimed solved.** An LLM cannot reliably distinguish "Sean's own instruction" from "content Sean pasted that happens to contain an instruction-shaped sentence." `ask_worker`'s trigger condition is Alex's own judgment during a real Sean-initiated turn — the same judgment call every other tool Alex already has relies on, not a new category of risk, but also not mitigated by anything specific to this capability. Worth real attention if `ask_worker` usage ever looks like it's responding to pasted/forwarded content rather than Sean's own words — visible in the rollup above, not prevented by the architecture.
8. **The guardrail, stated once, explicitly:** `ask_worker` is Q&A only. Any future use of it — by any session, under any time pressure — to get a worker to *act* on Alex's behalf is delegation, and must go through `worker.delegate_v1` (Part 2) once it exists, never around it through this capability's transport.

## Part 2 — Earned delegation rights (worker-to-worker), deferred, spec'd for later

**Unchanged core idea:** a worker doesn't get to delegate to another worker by default — it earns that right from its own track record, read from `getWorkerTrackRecord(workerSlug, tenantId)` (the commitment ledger, CODEX 101). Proposed: ≥80% done-on-time-or-late vs. expired, and ≥10 closed commitments, before `worker.delegate_v1` passes for that worker. A worker with `reliabilityRate: null` fails by construction — no track record is not a passing track record.

**Corrected/sharpened by the second red-team pass, for whenever this is actually built:**
- **The reliability metric must be checked for gameability before it's trusted**, not assumed sound because the number is high. Commitment difficulty isn't normalized today — a worker (or whoever assigns it work) could pad its record with easy commitments specifically to clear the bar. Whatever assigns commitments toward delegation eligibility needs its own honesty check before the threshold means what it's supposed to mean. Not resolved here — named as a real precondition for trusting the metric, not a footnote.
- **"A commitment" must mean the same thing across worker types** before comparing an 80%/10 threshold across different workers is a like-for-like comparison. Not yet true — the commitment ledger doesn't currently normalize commitment difficulty or type by worker.
- **The gate must be checked continuously, not once at earning time** — CODEX 100's own round-2 lesson (a Gmail watch persisting after gates start failing) applies directly here. If a worker's reliability craters after earning delegation rights, the *next* delegation attempt must re-check `worker.delegate_v1` fresh, not read a cached/persistent "earned" flag. Revocation must be automatic on re-check, not dependent on a human noticing and pulling it by hand.
- **Exactly one code path may check this gate — verified, not assumed.** CODEX 100 found a second, ungated activation path (the Cloud Scheduler renewal job) that nobody thought to check until a red-team pass looked for it. Before Part 2 is built: confirm there is no plausible admin/manual override (a Firestore flag, an emergency route) that could grant delegation without going through the track-record gate — the same shape of bypass, for a different capability.
