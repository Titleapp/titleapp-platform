# CODEX 102 — Alex's `ask_worker` Capability, and Earned Delegation Rights

**Status:** Scoped 2026-09-23, revised same night after two red-team passes caught real design gaps before anything was built — the cheap moment to fix them. Not yet built. Sean approved v1 for build; the redesign below is what should actually get built, not the first draft.

**Sean, 2026-09-23**, on the "staff meeting" discussion: workers stay siloed from each other — that isolation is a deliberate security boundary (CODEX-S52.65), not something to remove. The one exception: Alex should be able to reach into any worker's silo on request, audited, not a live multi-agent meeting. Separately, on delegation generally: *"It seems like there should be some method of earning the trust of the platform before you can delegate to others. Otherwise we might end up with the lazy bossy coworker syndrome."*

---

## Red-team pass round 1 (2026-09-23, before any code exists)

The first draft undersold what `ask_worker` actually does. Caught before building, not after:

1. **"Audited" implies contained; it isn't.** `ask_worker`'s mechanism means Alex's effective data access becomes the union of every worker's data access, gated only by a rate limit and after-the-fact logging — both throttle/detect controls, not access-boundary controls. This doesn't remove the silo boundary Sean wants kept, but it does bridge across every silo at once, controlled by nothing but Alex's own judgment about what to ask. Named explicitly below rather than left implicit in "audited."
2. **Does it only return an answer, or can it trigger actions?** The first draft didn't say. If `ask_worker` runs the target worker's *full* response-generation path including its normal tool-calling, Alex asking Max a question could cause Max to *act* — draft something, update a record, clear a queue — not just answer. That's a materially bigger deal than a visibility question. **Resolved below: `ask_worker` is answer-only, structurally, not by convention.**
3. **"Sean-initiated only" was a stated intent, not an enforced fact** — the exact pattern CODEX 100 found wasn't real until it was an IAM grant. Fixed below by construction, not by a gate predicate promising to check caller context.
4. **Indirect injection.** If Sean pastes forwarded content or a document into his message to Alex, and the trigger condition for `ask_worker` is just "reachable from Sean's message," attacker-controlled content could get Alex asking questions Sean never intended — same class of risk CODEX 97's risk register already names for inbound email. Not solvable by architecture alone; named as an accepted, open risk below, not claimed as solved.
5. **Rate-limiter reuse was ambiguous** — same bucket or same pattern, global or per-target-worker. Resolved below: separate bucket, global scope.
6. **No aggregate view of usage** — ironic, given the capability exists specifically to prevent Alex over-relying on asking instead of reasoning, and there was no way to actually see that pattern forming. Added below.
7. **"Registered in `capabilityGates.js`" without a stated predicate.** If the only real condition is "rate limit not exceeded," that's the rate limiter doing its job, not a distinct capability gate — pretending otherwise overstates the governance. Corrected below to be honest about what v1 actually gates on.
8. **`ask_worker` as a future delegation shortcut.** Not a flaw in the design, a risk to the design holding — a future session under time pressure could reuse `ask_worker`'s transport as an informal stand-in for real delegation once it exists, since delegation is deliberately harder to get. Named explicitly below as a one-line guardrail.
9. **Part 2 (delegation) gaps**, all still-deferred since Part 2 isn't being built now, captured for whenever it is: the reliability metric is gameable if commitment difficulty isn't normalized and "a commitment" isn't defined consistently across worker types; the doc didn't say whether the gate is checked once (earned, then cached) or continuously (CODEX 100's own round-2 lesson: continuous, not just at activation); and nothing guarantees a single enforcement path, the same shape of gap CODEX 100 found with the Gmail Cloud Scheduler job.

## Red-team pass round 2 (2026-09-23, still before any code exists)

Cleaner draft — most of round one's holes got closed by construction rather than promised. Fresh issues:

1. **"No side-effecting tools" needs to cover indirect/deferred effects, not just synchronous ones.** Stripping the target worker's tools for this call closes calls that mutate state synchronously within the turn. It doesn't automatically close a path where a worker's normal turn can write to a queue, mark something for later processing, or leave a note a later cron job reads and acts on — those are still side effects, just delayed ones, and "no tools available in this call" only closes them if those mechanisms are themselves tools that get stripped too. **Resolved below: the removal is scoped to every mechanism that can cause a future effect, not just synchronous tool calls, verified per-worker at build time.**
2. **Point 3 (chat-history logging) needs to be reconciled with point 1, explicitly.** Logging the Q&A into the target worker's chat history is itself a write. Left ambiguous, "no side-effecting tools available" and "the exchange gets logged" sit next to each other without confirming they don't quietly contradict. **Resolved below: the logging write is Alex's own orchestration code, never a tool handed to the target worker.**
3. **"Global" rate limit — global across what?** Fixed worker-scope gaming (global across target workers) but didn't say whether the 10/hour bucket is global across the whole platform or scoped per tenant. SOCIII spans multiple tenant contexts — a platform-wide bucket would mean one tenant's Alex activity throttles an unrelated tenant's. **Resolved below: per-tenant.**
4. **`workerSlug` scoping is the sharper version of the silo-bridging risk already named.** Round 1's point 1 named union-of-access risk *within* a tenant. The sharper version: does `ask_worker(workerSlug, question)` validate `workerSlug` belongs to Sean's current tenant, or could it reach a worker instance belonging to a different customer entirely? Unscoped, this isn't "Alex can see across silos it shouldn't casually bridge," it's a cross-customer data boundary — a different severity class entirely. **Resolved below: tenant-scoped by construction, the same way "no separate entry point" was made true by construction rather than promised.**
5. **What happens when the rate limit denies the call — not addressed.** If Alex hits the ceiling mid-conversation, does it tell Sean it couldn't check, or silently fall back to answering from its own reasoning with the same confident tone it'd use if it *had* asked? The second failure mode is worse than not having `ask_worker` at all — Sean would have no way to tell "verified with Max" from "Alex guessed." **Resolved below: a missing behavior spec, now specified.**
6. **The rollup doesn't carry the information the indirect-injection point needs.** Round 1's point 7 claimed injection risk is "visible in the rollup" if usage looks like it's responding to pasted content, but the rollup as scoped only captured volume/pattern data (counts, which workers), not anything about what triggered a given call. **Resolved below: rollup widened with one boolean flag, not message content.**
7. **Guardrail #8 is real work only if #1 has a gap — worth stating which.** If "no side-effecting tools, ever" fully holds, the guardrail against reusing `ask_worker` as an informal delegation shortcut is structurally unnecessary. If it doesn't fully hold, the guardrail is doing real, unenforced-by-code work — the exact "stated intent, not enforced fact" pattern round 1 called out. **Resolved below: now that #1 is tightened to cover deferred effects, the guardrail is stated as documentation/defense-in-depth, not as the only thing standing between the design and misuse.**
8. **Part 2 — the reliability metric rewards "eventually done" the same as "on time."** "≥80% done-on-time-or-late vs. expired" — on-time and late count identically. A worker consistently late but never expired scores the same as one consistently prompt, which seeds a subtler version of the exact "lazy bossy coworker" pattern one level down the chain, once delegation creates timing-sensitive downstream dependencies. **Resolved below: on-time and late now tracked separately for the delegation gate specifically.**
9. **Part 2 — sequencing between `worker.delegate_v1` and pillar-3 depth bounds isn't stated as a hard dependency.** Track record and pillar-3 bounds (max depth, max team lifetime, cost ceiling, cycle detection) are both required and neither substitutes for the other — correct, but not stated as a build-order blocker. If a future session builds the reliability gate first because it's more concrete and ready-to-build, two reliable workers could chain delegation with no depth limit until pillar-3 catches up — the same "built ahead of its own prerequisite safeguard" pattern CODEX 100 already demonstrated once in this system. **Resolved below: stated as an explicit hard blocker.**

## Part 1 — `ask_worker`, redesigned

**What it is:** a tool Alex can call mid-conversation — `ask_worker(workerSlug, question)` — that gets a real, grounded answer from that worker's own knowledge/rules/data, for Alex to relay or synthesize into its reply to Sean.

**What it explicitly is not, now enforced by construction, not just stated:**

1. **Answer-only, structurally — now scoped to every mechanism that can cause a future effect, not just synchronous tool calls.** The underlying call `ask_worker` makes runs the target worker's response-generation path in a mode with **zero write-capable tools bound** — not "the obvious action tools removed," every tool whose execution has any write path, including delayed ones: queue writes, "flag for later," "leave a note," anything a future cron job or another turn could read and act on. **Round 2 correction:** "no side-effecting tools" only closes the loop if that net is cast over every such mechanism, not just calls that mutate state synchronously within the turn — a worker could otherwise still be made to *cause* something downstream via `ask_worker`, just with a delay that makes it look unrelated. **Build-time requirement, not just a design claim:** before `ask_worker` ships for a given target worker, its full tool list must be reviewed and confirmed zero-write, and any new tool added to that worker later must be re-checked against this — a one-line addition to that worker's own tool-registration review, not a separate process.
2. **No separate entry point — closes the CODEX 100 dual-path class of bug before it can happen.** `ask_worker` is never its own HTTP route and never independently callable. It exists only as a tool binding inside Alex's own `/chat:message` request handler — reachable only while a real, authenticated turn from Sean's own session is actively being processed. There is no second path (no scheduled job, no other worker's turn, no admin route) that can reach it, because there is nothing else to call. This is what actually makes "Sean-initiated only, not autonomous" true, rather than a description of what nothing else happens to call yet.
3. **Visible, not a backchannel — and not a hole in point 1.** The question and answer get logged into the target worker's own chat history, tagged as invoked by Alex on Sean's behalf. **Round 2 correction, stated explicitly so it doesn't quietly contradict point 1:** this write is performed by Alex's own orchestration code, calling the target worker's chat-history collection directly — it is never a tool handed to the target worker as an exception to "zero write-capable tools bound." The target worker itself still has no write path in this call; the log entry is Alex writing about the target worker, not the target worker writing.
4. **Bounded, and now concretely specified — per-tenant, not platform-wide.** A dedicated rate-limit bucket — `alexAskWorkerBudget`, its own Firestore doc, not sharing state with `personaSendRateLimiter.js` (same pattern, separate instance, so a burst of persona-email sends can't eat into or be eaten by this budget). **Global across all target workers within a tenant** (10/hour per tenant, tune after real usage), not per-target-worker (per-worker would let Alex spread 10/hour × N workers, defeating the actual goal) and not platform-wide across tenants (**round 2 correction** — SOCIII spans multiple tenant contexts; a platform-wide bucket would mean one tenant's Alex activity throttles an unrelated tenant's). Bucket key is `{tenantId}`, matching this codebase's own tenant-scoping invariant (CLAUDE.md).
4a. **`workerSlug` resolution is tenant-scoped by construction — round 2 addition, the sharper version of point 1's silo-bridging risk.** `ask_worker(workerSlug, question)` resolves the target worker instance within Alex's own calling tenant context only — the same tenant boundary every other worker-scoped query in this codebase already enforces (CLAUDE.md's "tenant scoping is mandatory" invariant). There is no code path by which a `workerSlug` can resolve to a different customer's worker instance; this isn't "Alex can see across silos it shouldn't casually bridge," it would be a cross-customer data boundary if unscoped, a different severity class, so it's made true by construction rather than promised — same treatment as point 2's "no separate entry point."
5. **The gate, honestly specified.** `ask_worker` does not get a separate `capabilityGates.js` registration pretending to check something beyond the rate limiter — that would overstate the governance for no real benefit. Its one real, enforced condition is the rate-limit budget above, checked transactionally before the call proceeds, fail-closed. If a genuinely separate condition is ever needed (e.g., "don't ask a worker that's itself suspended"), that's a new, named, justified gate — not implied by registering in the same file other gates happen to live in.
5a. **What happens on a rate-limit denial — round 2 addition, a missing behavior spec, now specified.** A denied call must surface to Sean as a visible, honest statement — "I couldn't check with Max, this hour's budget is used up" — never a silent fallback to Alex's own reasoning delivered with the same confident tone it would use after a real answer. Silently swallowing the denial is a worse failure mode than not having `ask_worker` at all: Sean would have no way to tell "verified with Max" from "Alex guessed." This is a hard behavioral requirement on Alex's own response construction, not just a nice-to-have UX detail.
6. **A visible rollup of usage, now carrying enough to support point 7 below.** `alexAskWorkerBudget`'s doc (or a small `alexAskWorkerLog` alongside it) is readable by Dev, extending Dev's existing pattern (`workerCanary.js`'s "Dev cannot be the only thing checking Dev" logic) so a volume spike or a suspicious cross-silo fishing pattern is actually detectable in one place. **Round 2 addition:** each log entry also carries one boolean flag — whether the triggering message to Alex included pasted/forwarded content (a signal already cheap to detect, e.g. block-quoted or clearly non-conversational text) — not the content itself. Narrows the gap between what point 7 claims the rollup shows and what it actually captured.
7. **Indirect injection — named as an accepted, unresolved risk, not claimed solved.** An LLM cannot reliably distinguish "Sean's own instruction" from "content Sean pasted that happens to contain an instruction-shaped sentence." `ask_worker`'s trigger condition is Alex's own judgment during a real Sean-initiated turn — the same judgment call every other tool Alex already has relies on, not a new category of risk, but also not mitigated by anything specific to this capability. Worth real attention if the rollup's pasted-content flag (6, above) starts correlating with `ask_worker` calls — visible in the rollup, not prevented by the architecture.
8. **The guardrail, stated once, explicitly — and its actual status named, per round 2.** `ask_worker` is Q&A only. Any future use of it — by any session, under any time pressure — to get a worker to *act* on Alex's behalf is delegation, and must go through `worker.delegate_v1` (Part 2) once it exists, never around it through this capability's transport. **Given point 1's tightened scope (zero write-capable tools, including deferred-effect ones, verified per-worker at build time), this guardrail is currently redundant with code enforcement, not the only thing standing between the design and misuse** — stated here as documentation for future sessions and as defense-in-depth, not because a known gap depends on it. If point 1's build-time verification is ever incomplete for some worker, that status flips, and this guardrail becomes load-bearing rather than a restatement — worth re-checking this line's truth whenever a new worker gets `ask_worker` reachability.

## Part 2 — Earned delegation rights (worker-to-worker), deferred, spec'd for later

**Unchanged core idea:** a worker doesn't get to delegate to another worker by default — it earns that right from its own track record, read from `getWorkerTrackRecord(workerSlug, tenantId)` (the commitment ledger, CODEX 101). Proposed: ≥10 closed commitments and an on-time rate (see below) above threshold, before `worker.delegate_v1` passes for that worker. A worker with `reliabilityRate: null` fails by construction — no track record is not a passing track record.

**Corrected/sharpened by round 1, for whenever this is actually built:**
- **The reliability metric must be checked for gameability before it's trusted**, not assumed sound because the number is high. Commitment difficulty isn't normalized today — a worker (or whoever assigns it work) could pad its record with easy commitments specifically to clear the bar. Whatever assigns commitments toward delegation eligibility needs its own honesty check before the threshold means what it's supposed to mean. Not resolved here — named as a real precondition for trusting the metric, not a footnote.
- **"A commitment" must mean the same thing across worker types** before comparing a threshold across different workers is a like-for-like comparison. Not yet true — the commitment ledger doesn't currently normalize commitment difficulty or type by worker.
- **The gate must be checked continuously, not once at earning time** — CODEX 100's own round-2 lesson (a Gmail watch persisting after gates start failing) applies directly here. If a worker's reliability craters after earning delegation rights, the *next* delegation attempt must re-check `worker.delegate_v1` fresh, not read a cached/persistent "earned" flag. Revocation must be automatic on re-check, not dependent on a human noticing and pulling it by hand.
- **Exactly one code path may check this gate — verified, not assumed.** CODEX 100 found a second, ungated activation path (the Cloud Scheduler renewal job) that nobody thought to check until a red-team pass looked for it. Before Part 2 is built: confirm there is no plausible admin/manual override (a Firestore flag, an emergency route) that could grant delegation without going through the track-record gate — the same shape of bypass, for a different capability.

**Corrected/sharpened by round 2, for whenever this is actually built:**
- **On-time and late must not count identically toward the delegation gate — round 2 correction.** The original "≥80% done-on-time-or-late vs. expired" treats a consistently-late-but-never-expired worker the same as a consistently-prompt one. Once delegation creates timing-sensitive downstream dependencies (a delegated task blocking someone else's work), earning delegation on a "technically not expired" record seeds a subtler version of the exact "lazy bossy coworker" pattern Sean's trying to prevent, just one level down the chain. Fixed: the delegation-eligibility gate specifically tracks **on-time rate** as its own number (distinct from the ledger's general done-vs-expired view elsewhere, which can keep treating late-but-done as a lesser negative than expired) — proposed ≥80% strictly on-time, not on-time-or-late, plus the existing ≥10 closed-commitments floor. The exact threshold is Sean's call at build time; the structural fix (don't conflate the two states) is the part settled here.
- **`worker.delegate_v1` is hard-blocked from shipping until pillar-3 bounds exist — round 2 correction, stated explicitly rather than implied.** Track record and pillar-3 depth/lifetime/cost/cycle-detection bounds are both required and neither substitutes for the other — that was already true, but wasn't stated as a build-order dependency. Named explicitly now: **if a future session builds the reliability gate first because it's the more concrete, ready-to-build piece, `worker.delegate_v1` must not go live for real delegation until pillar-3's bounds also exist and are wired in** — otherwise two independently-reliable workers could chain delegation with no depth limit at all, the same "built ahead of its own prerequisite safeguard" pattern CODEX 100 already demonstrated once in this system (the Gmail Cloud Scheduler job). The reliability gate can be built and tested in isolation; it cannot be the only thing standing between "no delegation" and "delegation" in production.
