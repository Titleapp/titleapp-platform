## 1. Executive Summary

- **This is a real, active, well-funded market — not an empty field.** Abridge, Epic (AI Charting, shipped Feb 2026), Nuance DAX, Suki, and Nabla are all real, deployed competitors. Penn Medicine already runs ambient AI documentation for 600+ nurses, not just physicians. It is not RAAS — no independent rules layer validates the draft against documentation/coding standards *before* it's presented for approval; it's "AI drafts, human catches mistakes," not "AI drafts, rules validate, human approves an already-vetted result." This is specifically a **documentation-completeness** claim, not a medication-safety claim — see the risk-tier split in §3.1 before assuming this extends to MAR entries. See §4.

## 3. The Confirmed Gap — RAAS vs. "Human Catches Mistakes"

Directly fetched from Abridge's own nursing platform page (not inferred from marketing copy elsewhere):

- Captures nurse-patient conversation.
- Produces **draft flowsheet rows** — real structured EHR fields, not just free-text summary. This is a genuinely good, real capability; don't undersell it.
- **Linked to the source** — a nurse can trace a draft entry back to the conversation it came from. A real, useful audit-adjacent feature.
- **A human reviews and verifies before anything hits the chart.**

What's absent from everything found: an independent rules/compliance layer that validates the AI's draft against explicit, tenant-configurable documentation standards (ANA documentation guidelines, State Board requirements, institution-specific charting policy, coding-support requirements) *before* the human ever sees it — with that validation step itself immutably logged. Abridge's own "Custom Governance Control" language (mentioned as an enterprise feature) reads as admin/access-control governance, not content-compliance validation — worth confirming directly with Abridge material if this ever becomes a head-to-head competitive claim, but nothing found contradicts this read.

This is exactly SOCIII's RAAS invariant already proven elsewhere in the platform: agents propose, the rules engine validates, only then does a human see it for approval, and every step — including what the rules engine caught or waved through — is part of the permanent record. Applying that same invariant to nursing charting is not a new architecture to invent; it's the one already running in production for other verticals.

## 3.1 Two Things This Document Was Silent On, Now Addressed

**How does the data actually get captured?** Every competitor named in §2 is built around ambient voice capture — the nurse talks (to the patient, or narrating an observation), the system listens, structured entries get drafted from that conversation. That's the product, not an implementation detail underneath the RAAS question. If SOCIII's version instead expected a nurse to type into a chat interface, that would be a real regression versus what Abridge/Epic/Nuance/Suki/Nabla already ship, in a bedside environment (gloved hands, hands full, moving between patients) that's if anything less typing-friendly than the aviation cockpit case already flagged in CODEX 85. **The answer: voice (and photo, where relevant) capture via wearable is the intended input method**, using the same capture pipeline scoped in CODEX 87 (same session) — RealWear for Ruthie's program specifically, per the hardware decision made this session, with a phone mic as the interim stand-in before hardware is in hand. This document assumes that capture path; CODEX 87 owns the actual pipeline build, and per §8 item 5 nursing's access to it isn't yet prioritized ahead of aviation/MX.

**Recording a patient conversation is a real consent question, not a detail underneath the capture answer.** Directly verified: 11 U.S. states require *all-party* consent to record a conversation — recording a patient encounter without it is a real legal exposure, not a theoretical one. There's a live case: an April 2026 federal lawsuit (N.D. Cal.) against two healthcare organizations specifically alleging ambient-AI recording and transmission of patient-provider audio without prior consent. Every named competitor almost certainly handles this as a product feature (verbal disclosure at the start of the encounter, opt-out, Notice-of-Privacy-Practices language), not an afterthought — this needs to be built the same way, not bolted on later. See §8.1 for where this is now costed.

**Medication/MAR charting is not the same risk category as documentation completeness — and the boundary is about what a rule does, not which document it's attached to.** §6 originally listed a MAR (medication administration record) entry alongside a nursing note, flowsheet entry, and care plan as if they were all just "documentation types" a rules engine validates the same way. A nursing note being incomplete is a documentation/billing-compliance problem — real money (§4), but not a patient-safety decision. An AI system drafting or validating a *medication* entry touches dosage, timing, and interaction-checking — actual clinical-safety territory, with a materially different regulatory posture. Directly verified this session: the FDA's January 2026 Clinical Decision Support guidance (replacing the 2022 version) defines "Non-Device CDS" exemption criteria under the 21st Century Cures Act — software that presents a **single, specific clinical recommendation** (their own example: "initiate this medication at this dose") **fails** that exemption and becomes a regulated medical device, rather than exempt documentation software. But the safer classification isn't "MAR vs. everything else" — a completeness rule on a *non*-MAR field (e.g., "flag if an allergy check wasn't completed before a medication was charted as given") can still substantively function as a clinical-safety judgment even though it's nominally a completeness check on the wrong document type. **The real test: does this rule's output ever function as a clinical recommendation, regardless of which document type it's attached to.** If yes, it's the higher-liability tier no matter what it's called. The first ruleset built (§8 item 2) should be evaluated against that test, not just checked against a MAR/non-MAR document list.

## 4. The Billing/Compliance Case

Real, sourced figures (2025-2026 data):

- Hospitals spent an estimated **$43B in 2025** attempting to collect payment from insurers for care already delivered, including **~$18B** specifically overturning claim denials.
- **35% of claim denials trace to documentation issues.** 41% trace to billing errors more broadly.
- **80% of U.S. medical bills contain at least one error** (wrong codes, duplicate charges, missing information).
- Initial denial rate was **11.81% in 2024** and rising; **65% of denied claims are never resubmitted** — that's not delayed revenue, it's lost revenue.
- Reworking a single denied claim costs **$25–$181**; appealing one averages **$40–$45** in pure administrative cost, before the underlying revenue is even recovered.

The pitch this supports: a charting tool that validates against documentation-completeness rules *at the point of charting* — not after the fact — has a direct, quantifiable claim on reducing the 35% documentation-driven share of denials. This is a stronger sell to an institution's finance/compliance side than "saves nurses time," even though the time-savings pitch (what Abridge and Epic both lead with) is real too and shouldn't be dropped — it's additive, not a replacement pitch.

## 6. What Exists Today vs. What's New

- **Exists, live in production (CODEX 82):** clinical competency evaluation and attestation — an instructor signs off that a student demonstrated a specific competency (e.g., "Medication administration safety"), NCLEX-readiness tracked by the eight ANCC/NCLEX domains, real authorization/tenant-linkage work shipped 2026-08-29.

A MAR entry is listed separately, deliberately: per §3.1, medication charting carries a different regulatory risk tier than general documentation and should not be assumed to work the same way or be built first. This is genuinely adjacent to, not a subset of, the competency-evaluation system. They should likely share the same student/patient-case data model where real overlap exists (a charted note *is* evidence a competency was demonstrated), but this needs to be a real design decision, not assumed — see §8.

## 7. Recommended Approach

Start with UH Maui — the existing, real relationship, the CET production pipeline already live (CODEX 82), and Ruthie as the program owner already testing SOCIII's nursing tools directly. But build the charting engine so the same one works for a real working nurse, not a simplified "student version" that gets rebuilt later for production use. Concretely: the rules ruleset (documentation standards, required elements, billing-support requirements) should be real and institution-configurable from day one, even if the first deployment only ever runs it against simulated/practice cases — swapping "practice case" for "real patient encounter" should be a data-source change, not an architecture change.

**That claim depends on the consent workflow (§3.1, §8.1) shipping during the practice-case build, not after it.** If the disclosure/opt-out workflow is deferred because "practice cases don't need it," the eventual swap to real patient encounters isn't purely a data-source change anymore — it's a data-source change plus a consent-workflow build that was never exercised in production, with all the risk of an unproven feature going live for the first time exactly when the stakes are highest. The "just swap the data source" pitch only holds if consent UX is built and exercised (even in a simplified or no-op form, per CODEX 87's "no patient-adjacent, full stop" boundary for phase 1) from day one — not treated as something to add later because it doesn't seem urgent yet.

This mirrors the DPP authorized-agent lock-in logic directly: a nursing student who trained on this charting engine, whose muscle memory and trust in the tool was built during school, is a natural continued user once they're a working nurse — the same reason being the party who trains someone is worth more than being a swappable tool they pick up later.

**This pitch is conditional, not settled.** It assumes the working-nurse version is the same system the student trained on, continuing forward. But §8 item 3 leaves genuinely open whether real-world deployment means integrating with the institution's actual EMR of record (Epic, Cerner) or building a standalone SOCIII-owned charting record. If the answer is standalone, a working nurse still has to chart in Epic for the official record — SOCIII's tool becomes a *second* system alongside it, not a replacement, which is a meaningfully weaker lock-in story and a real adoption-friction risk (nurses already resent redundant documentation). This section's pitch holds if #3 resolves toward real EHR integration or toward SOCIII's record becoming the institution's system of record; it needs revisiting if it resolves toward "standalone tool alongside Epic."

## 8. Open Decisions for Sean

1. **Data model relationship to the existing competency-evaluation system** (§6) — should a charted note be able to serve as evidence toward a competency attestation, or should these stay fully separate systems that happen to share a student roster? Real design decision, not obvious either way.
2. **Which documentation standard to encode first — deliberately steering away from anything that functions as a clinical recommendation.** Per §3.1's risk-tier split, the first ruleset should be evaluated by what its output does, not just which document type it's attached to: a rule flagging a missing signature or timestamp is safely in the documentation-completeness tier; a rule flagging a missing allergy check, an incomplete vitals field tied to a medication decision, or anything MAR-related risks crossing into clinical-recommendation territory even if it's framed as "just completeness." Pick the first ruleset (e.g., a med-surg flowsheet's structural/administrative fields) by applying that test explicitly, not by document-type alone.
3. **Real-world (working-nurse) deployment path** — real EHR integration (Epic/Cerner) vs. a standalone SOCIII-owned charting record. This is not just an integration-effort question — per §7, it directly determines whether the lock-in pitch holds or whether SOCIII becomes a second system alongside the institution's real EHR. Should be decided before UH-specific work goes far past the practice-case stage.
4. **Competitive positioning specifics** — before any public claim that no competitor has RAAS-equivalent validation, this should be directly confirmed against Epic AI Charting specifically (the highest-stakes unknown, per §1) and against Abridge's actual enterprise governance documentation (their "Custom Governance Control" feature) — not rest on this session's Abridge-only page-fetch.
5. **Capture method for the practice-case (UH) deployment specifically** — §3.1 assumes voice/wearable capture per CODEX 87, but that hardware (RealWear) is being scoped/tested there on aviation/MX tasks first. Worth deciding whether nursing charting's first practice-case build waits for that pipeline to prove out on CODEX 87's crawl/walk stages, or gets its own phone-mic-based capture path in parallel rather than queuing behind aviation.

### 8.1 The Compliance Lift This Doc Undersold

Real patient data — even practice-case data that's structured to look like real charting — puts this in a materially different compliance posture than anything else built this session. This deserves the same explicit costing CODEX 84 gave its prerequisite work and CODEX 85 gave its operational-overhead section, not a clause inside a bullet:

- **A Business Associate Agreement (BAA)** with any institution whose data touches real (not synthetic) PHI — a real legal/contracting step, not a technical one, likely requiring outside counsel review.
- **HIPAA technical safeguards** — encryption at rest and in transit (likely already true given existing platform patterns, but needs explicit confirmation for this specific data path), access logging, minimum-necessary access controls, breach-notification procedures.
- **Recording consent, as its own real workflow, not a HIPAA sub-bullet — and it applies to the practice-case phase too, not just the eventual real-patient phase.** 11 U.S. states require all-party consent to record a conversation; there is a live federal lawsuit (April 2026, N.D. Cal.) against two healthcare organizations specifically for recording/transmitting patient-provider audio via ambient AI without prior consent. That all-party-consent framing doesn't exempt a scenario just because the "patient" isn't real: if a practice-case scenario has a student recording a **standardized patient or a classmate role-playing a patient**, that's still a real, live person being recorded, and their consent is required under the same logic — this was raised in the CODEX 87 conversation and needs to be resolved here too, not left implicit. This needs a real disclosure/opt-out workflow (verbal disclosure at encounter start, Notice-of-Privacy-Practices language, an actual opt-out path) designed as a product feature before any audio of another real person is captured, practice-case or not — not assumed to be covered by the BAA, and not assumed to only matter once real patients are involved. **Add to the Ruthie conversation (§9): does the practice-case scenario ever involve recording another live person (standardized patient, classmate) at all — if yes, has consent for that specific scenario been designed for, separately from the eventual real-patient case?**
- **Possible SOC 2 or HITRUST**, depending on the institutional counterparty's own requirements — this is a multi-month lift on its own if a customer requires it, not a checkbox.
- **The deferral logic below assumes "practice case" means "synthetic" — confirm this with Ruthie before relying on it.** If UH's practice charting is built on genuinely fabricated case libraries (DocuCare/SimChart's model), this whole compliance lift defers cleanly until real-EHR-touching deployment is scoped. But nursing documentation exercises commonly have students chart based on their actual clinical rotation experiences — a real patient encounter, written up as a practice note, sometimes only lightly de-identified — not a purely synthetic scenario. If that's how UH Maui's program actually works, some of this compliance lift (recording consent specifically, and possibly BAA/HIPAA posture) may apply from day one of the practice-case deployment, not later. This is the same conversation §9 already flags asking Ruthie about (DocuCare/SimChart licensing) — add this question to it, don't treat the synthetic-case assumption as settled until she confirms it.
