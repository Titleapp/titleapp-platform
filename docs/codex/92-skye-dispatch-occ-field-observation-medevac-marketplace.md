# CODEX 92 — SKYE Dispatch: Real OCC Field Observation & Medevac Marketplace Concept

**Status:** Field-research + concept scoping doc. Nothing built. No code audit performed for this doc — this is primary-source observation of a real customer's (Life Flight Network) actual dispatch operation, cross-referenced against what's already known about SKYE Dispatch's current scope from prior sessions/CODEX docs.

**Origin:** Sean visited LFN's OCS/OCC (Operations Control Center) in person on 2026-09-16 and took ~24 photos of the real dispatch environment — screens, workstations, and a manual tracking spreadsheet. This doc reviews all of them directly (not summarized secondhand) and connects the findings to a real product idea Sean framed in his own words: a medevac request/fulfillment marketplace, analogous to Uber's tiered ride options.

---

## 1. Executive Summary

- **Real dispatch, today, runs across at least six disconnected systems, confirming Sean's "plate-spinning" description literally, not as a figure of speech.** In the photos: **FlightVector** (fv.lifeflight.org — live fleet map + aircraft list), **SkyRouter** (a separate commercial flight-following product — live position/altitude overlay), **OASIS** ("Operational Analysis & Systems Improvement Software" — a Life Flight-branded portal for clinical quality/safety workflows, *and* a structured historical mission log with real dispositions), a **Windows CAD-style "Record Management Entry"** tool (patient demographics, referral agency lookup, dispatch record fields), **TigerConnect** (a hospital-to-dispatch chat app carrying real, unstructured clinical transfer requests), and a **manual Excel "Communication Center Passdown"** workbook, updated shift-to-shift, with a real tab specifically for Hawaii.
- **The manual Excel passdown sheet is the single most important artifact — it's the literal, physical evidence of the gap Sean described.** It tracks OOS (out-of-service) aircraft, "Active Ground Request," "Unassigned Flight Requests," and an "Operational Rate" (73.3% in the observed screenshot) — by hand, per shift, per region (separate tabs per region, including one for Hawaii). This is a real, currently-in-production "honor system": no live cross-operator visibility, just a spreadsheet someone updates and hands off.
- **"Unassigned Patients" and "Unchecked Requests" already exist as real fields in professional EMS dispatch software** (seen in the combined ground+air active-asset CAD view) — this validates that the "which requests never got fulfilled" concept from CODEX 91 isn't a SOCIII invention; it's an established, if manually-tracked, industry concept SOCIII can build a genuinely better version of.
- **The actual transfer-request "payload" is real and mostly structured, just delivered as unstructured chat text.** The TigerConnect screenshot shows an actual interfacility transfer request with a clean, consistent field set: patient name/DOB/MRN, referring facility + physician + callback number, transfer-to facility, accepting physician, diagnosis, isolation status, weight, respiratory assist needs, special equipment, rider request. This is close to a ready-made API payload shape for a real request/dispatch system — it's just trapped in a chat app today.
- **The "Uber for medevac" framing is real and maps onto real, named transport tiers Sean already uses** — Rotor (scene call), Stable patient transport, Global patient transport, NEST, Balloon transport — these aren't invented category names, they're the actual product tiers this industry already thinks in. A marketplace that lets a requesting facility say "I need X" and see which of these tiers are actually available, instead of manually messaging and waiting for a reply, is a real, well-defined product shape.
- **This is a different, bigger concept than CODEX 91 — worth keeping the two separate.** CODEX 91 is retrospective analytics ("what happened, what didn't"). This is a live, transactional marketplace ("what's available right now, match it"). They should share underlying data (mission legs, trip requests) but are not the same build.

## 3. The Marketplace Concept, Stated Precisely (Sean's framing, organized)

A requesting facility (hospital, scene, another agency) states a need — patient acuity, origin, destination, required transport tier — and instead of manually messaging a dispatch center and waiting for a human-relayed reply (today's TigerConnect + Excel-passdown reality), the system shows **real, live availability across the actual transport-tier categories this industry already uses**:

- **Rotor / scene call** — helicopter response to an accident/incident scene.
- **Stable patient transport** — lower-acuity interfacility transfer.
- **Global patient transport** — long-distance/international patient movement.
- **NEST** — (specialized neonatal/pediatric transport team, per industry convention — the term appeared as a real base/post label in the observed screenshots, e.g. "Spokane Ground NEST").
- **Balloon transport** — (a specific fixed-wing or pressurized-transport category in this industry's own vocabulary).

This is the "Uber XL / Uber Green / Uber rideshare" analogy Sean drew: not one generic "request a medevac" button, but a tiered set of real, named product categories, matched against real-time availability — which today exists only as a manually-updated spreadsheet and ad hoc chat messages between a requester and one specific operator at a time (not a real market view across operators).

## 4. What This Connects To in the Actual Codebase (grounded, not assumed)

- **`av-dispatch-001`** already exists as a real SKYE worker (confirmed earlier this session via `_SUITE_PERSONAS` and the aviation suite audit) — this concept extends that worker's scope, it doesn't require a new one.
- **`dispatchTripRequests/{scopeId}/requests/{id}`** (`functions/functions/services/dispatch/tripRequests.js`, confirmed real and wired this session while scoping CODEX 91) already models "who wants this flight, where, who's on it" with a `requestedDepartureZulu` field — this is the right existing object to extend with a transport-tier field and a real-time availability-matching layer, not a reason to build a parallel schema.
- **`AV-032` (Crew Scheduling & Roster)** already calls out `AV-009` for duty-time/legality validation on every proposed assignment (confirmed via the RAAS rules doc read earlier this session) — any real-time matching engine **must** gate a match against the same legality check (crew duty time, aircraft airworthiness/MEL status via `computeAirworthiness`) before ever showing an asset as "available." This is not optional polish — an Uber-style "instant match" that ignores Part 135 legality would be a real safety and regulatory problem, not just a product gap.
- **HIPAA is a real, load-bearing constraint here, not a footnote.** The actual TigerConnect screenshot contained real patient-clinical-shaped fields (diagnosis, weight, respiratory status, isolation status). `AV-032`'s own P0.AV1 rule ("HIPAA compliance required for all medevac patient data handling") already exists as a platform-wide invariant — any marketplace request payload modeled on §1's field list needs to inherit that same discipline from day one, not have it retrofitted.
- **CODEX 91's mission-leg/unfulfilled-mission work is a real, natural data source for this**, but the two are not the same product: CODEX 91 answers "what happened historically" (retrospective analytics for shift planning); this concept is "what's available right now" (live matching). A shared underlying `dispatchTripRequests`/mission-leg data model can serve both, but the marketplace itself is new, live, transactional surface area — a bigger build than CODEX 91's heatmap/detection capabilities.

## 5. Open Questions (not yet resolved — this is a concept doc, not a build plan)

1. **Who is the counterparty?** Is this marketplace scoped within LFN's own fleet + contracted ground assets (an internal dispatch-efficiency tool), or genuinely cross-operator (competing medevac companies seeing each other's availability) — the latter is a much bigger trust/business-model question (would a competitor actually publish real-time availability to rivals?), not just an engineering one.
2. **Data source for real-time availability** — today's OOS/in-service status lives in the manual Excel passdown and the CAD tool observed in §2 items 7/9. Does SOCIII get real integration access to whichever CAD/OASIS-equivalent system holds this live, or is this bootstrapped from SOCIII's own dispatch/mission-leg data (§4) as adoption grows?
3. **Regulatory-legality gating (§4)** — needs real design work, not an assumption that "if AV-009 exists, it's handled." A live marketplace UI showing instant availability needs the legality check to run *before* display, not just before a human confirms — a materially different real-time performance/architecture requirement than a human-paced dispatch workflow.
4. **HIPAA data handling for the request payload (§4)** — what's the minimum necessary field set for a *matching* decision (transport tier, acuity level, origin/destination) versus what only needs to flow to the *accepted* operator (full clinical detail)? This is a real design question, not a detail to defer.
5. **Relationship to the existing manual passdown process** — does this replace the Excel workbook, or run alongside it during a transition period? Real operational tools like this rarely get replaced in one step; worth planning for a coexistence period.
