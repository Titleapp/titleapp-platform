# CODEX 81 — Grace's Actual Reach: Routing, Content-Freshness, and Adoption

**Status:** 🟡 two of three structural gaps built, round-2 red-teamed and hardened; the third (adoption) is a people problem, not a code one, and is specified but not "solved"
**Owner:** Sean / Claude Code
**Date:** 2026-08-27
**Trigger:** A red team on CODEX 80, evaluated against the actual bar CODEX 79 sets ("can this carry 99% of support load with zero human hires," not "is this a reasonable worker"), found that a well-written persona sitting on a static knowledge base with no cross-persona routing can't get anywhere near that number — no matter how good the prompt is. Sean: *"I think we have to step back here and rescope your codex."*

**What changed from CODEX 80:** CODEX 80 is now correctly scoped to just Grace's persona and system prompt — that part held up in review. This CODEX owns the three things that actually determine whether the no-FTE thesis is real: (1) does Grace ever see the traffic she exists for, (2) does her ceiling rise over time or stay fixed at day-one Locker content, (3) does anyone actually go to her instead of texting a person they already know. None of these are prompt-engineering problems.

## 1. Routing — built and verified this session

**The gap:** if a message like "I can't access the evaluation tool" is typed to Hannah (plausibly where most people land first), `ChatPanel.jsx`'s Layer 1 regex hard-intercepted it to human escalation before Grace — or anyone — ever got a chance. CODEX 80's fix only covered the case where Grace was *already* the active worker; it did nothing for the far more common case where someone is mid-conversation with a different persona entirely.

**What got built:**
- `ChatPanel.jsx`'s escalation logic is now a genuine three-way split: **explicit** human requests ("talk to a human") always intercept immediately, for every worker — overriding that would undermine real consent. **Implicit trouble** phrasing ("can't access X," "something's broken"), when the active worker is *not* Grace, now triggers a visible, deterministic handoff: a short message ("let me bring in Grace...") plus an actual worker switch, reusing the same `ta:select-worker` mechanism the platform already uses for the `[[SWITCH_WORKER:...]]` marker elsewhere (CODEX 50.28) — same pattern, just triggered client-side before any network call instead of parsed out of an LLM response. When Grace herself is already active, implicit-trouble phrasing falls through to her directly, as CODEX 80 originally specified.
- **A real dependency this surfaced:** the switch only works if Grace's slug exists in the live worker catalog (`digitalWorkers/*` in Firestore, read by `useWorkerCatalog()`). She wasn't in it — only in the backend's inline prompt registry. Added `/admin:bootstrap-program-support-001` (mirrors the existing Hannah bootstrap route exactly) to publish that catalog doc. **This route has to actually be run once, per the same "commit ≠ deployed" discipline CODEX 79 took five rounds to establish — it is not run yet.** Until it is, the code fails safe: `ChatPanel.jsx` checks for Grace in the catalog before attempting the switch, and falls back to the old human-escalation path if she isn't found.
- **Round-2 fix — the fallback is no longer only a `console.warn`.** A `console.warn` is invisible to anyone not watching devtools, and this is the single point of failure for the entire reach improvement — if the bootstrap step is forgotten, the system silently reverts to 100% human escalation on implicit-trouble phrasing indefinitely, with nothing surfacing that regression anywhere a person would see it. The fallback now also fires a non-blocking `POST /v1/support:routing-fallback`, which writes a queryable `alertFeed/platform-ops` entry (`type: grace_routing_fallback`) — the same visibility pattern the safetyContact gate uses on fail-open (CODEX 79 §0D).
- **Round-2 fix — Grace can hand a mis-routed question back.** The regex that can route a message *to* Grace has no semantic understanding — "I can't access the reasoning behind this diagnosis" contains "can't access" and would trigger the same switch as a genuine account question, but it's actually clinical content. Grace's prompt now explicitly names this failure mode and hands back via the same `[[SWITCH_WORKER:{{TUTOR_WORKER_SLUG}}]]` marker mechanism rather than attempting the question or leaving the person stuck with the wrong persona. `{{TUTOR_WORKER_NAME}}`/`{{TUTOR_WORKER_SLUG}}` join `{{PROGRAM_NAME}}` as the tenant-specific tokens in her otherwise reusable prompt.

**Explicitly still open — stated honestly rather than asserted away:** the reviewer's finding (no evidence the prompt-level "try first" instruction actually beats the universal SUPPORT ESCALATION append, which the code's own comment calls a "final override") is **still open** for the case where Grace is already the active worker and phrases something ambiguously. The routing fix sidesteps this for the Hannah→Grace handoff case specifically, but doesn't resolve it for someone who opens a conversation with Grace directly. The handback fix is unverified for the same underlying reason — whether Grace reliably recognizes "this is actually clinical" and emits the marker, rather than attempting an answer anyway, rests on the same LLM-instruction-following assumption as try-first and the `CONTENT_GAP` marker in §2. **These are one verification task, not three** — see §5 item 2.

## 2. Content-freshness loop — built this session

**The gap:** Grace's system prompt (correctly) tells her to say "I don't have that" rather than guess. But nothing described what happens to that miss afterward. Without a loop, the same gap recurs for the next person forever, and her effective ceiling is fixed at whatever the Locker happened to contain on day one — 99% never becomes achievable, only asymptotically approached by luck.

**What got built:**
- Grace's system prompt now instructs her to end a reply with `[[CONTENT_GAP: one-sentence description]]` — invisible to the person she's talking to — specifically and only when she's genuinely tried to help from her Locker and come up short. Not on every message; not instead of trying.
- `ChatPanel.jsx` parses that marker out of her response (same pattern as the `SWITCH_WORKER` marker), strips it from what the user sees, and fires a non-blocking `POST /v1/support:content-gap`.
- The backend route writes to a `supportContentGaps` Firestore collection: `tenantId`, `workerSlug`, the gap description, a `gapHash` (round-2 fix, below), `status: "open"`, timestamp. Fails silently (returns `ok: true` either way) so a logging failure never interrupts someone's actual conversation with Grace.
- **Round-2 fix — a frequency signal, so the log is prioritizable once someone reads it.** A raw per-entry log can't distinguish "ten unrelated one-off misses" from "the same missing FAQ item hit ten times this week" — the second is the actual priority, but ten identical-looking rows don't say so on their own. `gapHash` is a normalized hash (lowercase, whitespace/punctuation collapsed, scoped to tenant+worker) computed at write time, so frequency can be computed later with a simple `GROUP BY` without re-instrumenting anything. **Real limitation, stated honestly:** this is normalization, not semantic dedup — two differently-worded gaps about the same underlying issue ("can't reset my password" vs. "forgot my login") still hash differently and would need a smarter pass (embeddings, or an LLM-based clustering step) once there's enough volume to justify it.

**Explicitly still open:**
- **This is a log, not a closed loop.** Nothing currently reads `supportContentGaps` — no digest, no admin view, no automatic Locker update.
- **No default review cadence was proposed** (round-2 finding) — leaving "who reviews this and how often" fully open means the loop has no anchor if that conversation doesn't happen promptly; an unowned, unscheduled log is functionally identical to not having built it. **Default, overridable by Sean/Ruthie:** Ruthie reviews `supportContentGaps` weekly until told otherwise — not because that cadence is provably right, but because a wrong default that gets corrected beats no default that quietly never gets picked up.
- **The marker's reliability is itself unverified** (round-2 finding) — the whole "ceiling rises over time" claim depends on Grace consistently emitting `[[CONTENT_GAP:...]]` exactly when she's tried and failed, not more or less. A missed marker is a **silent failure by construction**: no error, no trace, nothing to notice unless someone independently samples her actual "I don't have that" responses and checks whether a gap got logged each time. That sampling check hasn't been done — it's a real verification task, not a code fix, and it's listed in §5.

## 3. Adoption — specified, not solved, because it isn't a code problem

**The gap, restated precisely:** the actual pattern that triggered this whole CODEX was Anne texting Ruthie, who texted Sean. Grace living inside the chat surface does nothing for that pathway unless Anne's own habit changes to "ask Grace first." No amount of routing or content-loop engineering fixes a behavior-change problem.

**Draft plan (2026-08-27) — concrete enough to send, still Sean/Ruthie's call to edit or approve:**

1. **Tell Anne Grace exists, framed as "try this first," not "here's what happens when something breaks."** Fold into the escalation-path summary CODEX 79 §4.4 already calls for sending before go-live. Draft line: *"For anything account- or access-related — adding someone, finding something, 'how do I' — try Grace first, right inside the platform. She's built specifically for that and available any time, not just business hours. If she can't help, she'll say so plainly and loop in a person directly."*
2. **A one-tap way to reach her, to close the friction gap named in round 2.** The platform already supports direct-linking to a worker via a `?persona=` URL parameter — a bookmarked link straight to Grace's chat (saved to Anne's phone home screen) is nearly as fast as opening a text thread, no new engineering required. Include that link, not just an instruction to "log in and find Grace," in the message from item 1.
3. **What Ruthie does the first few times Anne texts her out of habit instead.** Named risk, not fully solved: this asks Ruthie to do the harder thing (redirect) instead of the easier thing (just answer) under normal time pressure. Best available mitigation without more engineering: Ruthie answers if it's genuinely urgent, but for anything else replies with something like *"Try asking Grace this one — I want to make sure she's actually catching these,"* and only steps in herself if Grace couldn't help. This is a real habit-change ask of Ruthie specifically, not a guaranteed safeguard — flagged, not fixed.
4. **A separate, explicit check in weeks 1–2: did Anne ever contact Grace at all**, independent of what the deflection percentage says once it exists. A perfect deflection rate on zero volume looks identical to success and isn't — check via `supportWorkerActivity` for UH Maui's tenant showing any `totalTurns` at all before trusting the percentage to mean anything.

## 4. Structural ceiling — stated explicitly, per the reviewer's Tier 2 finding

The "always honor an explicit request for a human" design (§1) is the right call ethically — overriding someone's stated wish for a person would be worse than a lower deflection number. But it means **some fraction of traffic reaches for that phrase out of impatience or lack of trust, especially early on, regardless of how good Grace is.** This is a real, structural cap below 100%, not a bug to be engineered away. CODEX 79's ≥90% target should be read against this ceiling, not as if 100% were the honest asymptote.

**Refinement (round-2 finding):** that ceiling number actually bundles two different things — people who don't yet trust Grace and ask for a human out of impatience (a trust problem, fixable via adoption and track record over time), and people correctly asking for something Grace is barred from doing by design (an account change, a billing dispute) and should be routed to a human regardless of how good she is (a structural, permanent floor). Lumping both into one ceiling percentage will make it impossible to later tell which kind of gap is shrinking and which isn't. Once the deflection metric exists (§5), these should be counted separately, not folded into one number from the start.

## 5. Punch list — execution items, not open design questions

The red-team process converged (round 5): every remaining item below is "go do the thing," not "go figure out what's wrong." Two are now built on paper and just need to actually run against live traffic; the rest need Sean/Ruthie or a deploy, not more design.

1. **Deploy, then run `/admin:bootstrap-program-support-001`.** Nothing built across CODEX 79/80/81 is live yet — it's committed to git, not deployed (`firebase deploy --only functions` + the frontend build). Without the bootstrap running afterward, the routing fix fails safe to the old behavior every time (no longer silently — it now fires a queryable `alertFeed` entry — but the alert is not the fix).
2. **Get a live test transcript covering all three marker checkpoints together** (round-3 finding, unified): does Grace try to answer before escalating, does she hand back correctly on a mis-routed clinical question, does the `CONTENT_GAP` marker fire exactly when she comes up short and never when she doesn't. One test session, three checkpoints — a failure in one should lower confidence in all three.
3. **Deflection-rate report — built this session** (`scripts/graceDeflectionReport.js`), reading a new purpose-built `supportWorkerActivity` counter (incremented once per normal Grace turn via `POST /v1/support:worker-turn`) against existing `supportSessions` escalation records. Deliberately avoids deriving "total Grace conversations" from the general `chatSessions` collection, whose schema isn't consistent enough across this file's write sites to trust for this. **Not yet run against real data** — there isn't any until deploy + bootstrap + real traffic happen. Still reports one blended ceiling number, not split by §4's trust-vs-structural refinement — that split needs `supportSessions` to record which category an escalation falls into, which doesn't exist yet.
4. **Adoption plan — drafted this session** (§3), including a concrete message for Anne and a one-tap `?persona=` deep link to close the friction gap without new engineering. Still Sean/Ruthie's call to send as-is or edit.
5. **Confirm (or override) two stated cadence defaults**: Ruthie reviews `supportContentGaps` weekly; Sean glances at `alertFeed/platform-ops` weekly (covers both `safety_gate_check_error` from CODEX 79 and `grace_routing_fallback` from here). Both are placeholders precisely so the loop has an anchor even if this specific conversation doesn't happen right away — correct them if wrong, don't leave them silently unconfirmed.
6. **Single-tutor-per-tenant** (`{{TUTOR_WORKER_SLUG}}`) is a confirmed, deliberate v1 scope limit — matches UH Maui, the only real customer today. Revisit only when an actual multi-tutor tenant exists, not before.
