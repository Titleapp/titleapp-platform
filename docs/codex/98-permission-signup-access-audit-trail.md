## Red-team pass (2026-09-21)

A review of the first draft caught real gaps in how well this doc actually closes the loop it exists to close — recorded here rather than smoothed over, since this doc is specifically about tamper-evidence, so gaps in the tamper-evidence itself are the whole point.

1. **The doc's own "gap" section describes a bypass (role grants via direct Firestore writes/scripts) but the fix doesn't stop it.** Checked, and the suggested fix (Firestore security rules) turns out not to apply: `firestore.rules` already sets `memberships` to `allow write: if false` for client SDK — the client path was already closed, with an existing comment noting "Server writes via Admin SDK bypass these rules." **Rules cannot stop Admin SDK access, on any Firebase project — that's fundamental, not a gap in this codebase's rules specifically.** The real fix is different: checked whether Firestore Data Access audit logging is enabled for this project (the GCP-native mechanism that independently records every Admin SDK read/write with the performing identity, regardless of which application code path — or lack of one — triggered it). It is **not enabled** — queried Cloud Logging directly; zero `data_access` entries for `firestore.googleapis.com` despite heavy Firestore traffic all night. Turning this on is the actual fix for the bypass concern; a future audited "change role" endpoint is a courtesy for the honest path, not a guarantee against the dishonest one.
2. **`membershipEvents` rows are not yet tamper-evident, and the doc shouldn't imply otherwise.** The two shipped write sites create events with `batchId: null` — exactly as mutable as the field they're meant to make trustworthy, until the sibling batch-anchor job exists. Stated explicitly in Build Status now.
3. **No stated behavior for a consent request that times out unanswered.** Fixed below: "no timeout ever converts to approval" is now an explicit, named rule, not left to be quietly added later by someone optimizing for user friction.
4. **The consent model's "purpose" field was doing load-bearing work with no matching rule.** If purpose were ever free text or loosely matched, a new requester could phrase around an old approval. Fixed below: purpose values are a fixed, enumerated set, matched exactly — never substring or category matched.
5. **Anomaly detection was a bullet point, not a spec** — no threshold, window, response, or owner, for the backstop covering the worst-case scenario specifically. Fixed below with concrete values.
6. **This doc didn't reference CODEX 97's real-time nudge channel, risking a second "how does Sean get told" system getting invented.** Fixed: anomaly alerts and consent-request notifications now explicitly route through the same channel CODEX 97 built for external-facing actions.
7. **Access-event logging was deferred as "largest lift" without checking whether it's a live exposure today.** Checked: real `academic_record` and `clinical_evaluation` DTCs already exist in production under tenant `clearwater-nursing`, one dated 2026-06-18. This is live regulated student data, today, with no access-event logging — a present compliance gap, not a backlog item. Reflected in Build Status priority below.
8. **The three additional unaudited `memberships.add()` sites, and pipeline cost.** Checked: `index.js:739` (an auto-repair fallback, likely high-frequency — fires whenever a membership lookup misses but a workspace doc exists), `1145`, and `11924` (both live onboarding flows) are all real, active code paths, not dead code — a live-risk window until wired, not just a to-do. On cost: OpenTimestamps itself has no per-anchor fee (one Merkle root per day, batched — not a per-write blockchain transaction), so a second pipeline doesn't meaningfully add monetary cost; it does add a second Cloud Function's worth of operational surface to maintain and monitor, worth noting plainly rather than treating as free.

## Red-team pass, round 2 (2026-09-21)

Round 1's Data Access audit logging recommendation itself needed checking before executing, not just proposing — this round caught real gaps in the proposed fix and in several of the round-1 decisions.

1. **Data Access audit logging has a real cost/volume dimension round 1 didn't account for — RECALIBRATED, not yet enabled.** Firestore Data Access logs (`DATA_READ`/`DATA_WRITE`) are scoped by IAM policy at the *service* level, not per-collection — there is no native way to say "only log `memberships`." Enabling `DATA_READ` project-wide on a service with this session's own traffic volume would be genuinely expensive and high-volume. **Decision pending, not resolved**: proposed alternative is a scheduled reconciliation-check Cloud Function comparing `memberships`' current state against what `membershipEvents` predicts, alerting on mismatch — directly tests the actual threat (a write that bypassed the audited path) at a fraction of the cost of blanket logging. See Open Decisions.
2. **Checked the identity-granularity concern concretely rather than assuming — resolved cleanly, per Sean.** Verified via `gcloud auth application-default print-access-token`: local admin scripts run under `titleapp.core@gmail.com`, a real, distinguishable Google account — not an opaque shared service account. Sean confirmed this is his own dedicated ops/dev account, set up specifically to keep coding/infra activity out of his personal inbox, and he is the only one with access. So a Data Access log entry attributed to this account is meaningfully attributable: it's either legitimately Sean, or that one credential was compromised — the ordinary credential-security risk every account carries, not a gap needing a separate fix. No open item here.
3. **Anomaly-detection auto-suspend had no false-positive path.** A legitimate burst (e.g. an employer onboarding many former students at once) could trip the same threshold as a probing attacker. Fixed below: the suspended tenant gets a generic notice (that they're suspended, not why — avoids tipping off an actual bad actor) plus a defined 4-business-hour review SLA, so a false positive becomes bounded friction, not silent indefinite lockout.
4. **"No timeout converts to approval" left open whether an unanswered request expires to denied or stays pending forever.** Decided, not left conditional: a request unanswered for 7 days expires to **denied**, is deleted from the pending queue, and the requester must resubmit if still needed. Never converts to approved, and never sits in limbo indefinitely either.
5. **`index.js:739`'s prioritization wasn't explained.** Round 1 moved Data Access logging and access-event logging ahead of the sibling anchor job because they're live gaps, not hardening — `index.js:739` is exactly that same category (a live, likely high-frequency unaudited write path), and by that same logic belongs at the same priority tier, not below sign-up anchoring. Reordered in Build Status.
6. **Stacking anomaly/security alerts onto CODEX 97's real-time nudge channel sharpens the alert-fatigue risk that doc was built to avoid.** CODEX 97's channel was designed for external-facing actions (a send, a post) — a possible-security-incident alert is a materially higher-stakes category, and if both look identical in the same SMS/Telegram stream, the one that can least afford to get lost is the one most likely to. Fixed below: anomaly/security alerts on this channel must carry a distinct, visible marker (e.g. a `[SECURITY]` prefix) and are never batched/summarized the way a routine external-action nudge can be.
7. **`contentHash` field coverage — checked, confirmed correct.** `membershipEvents.js`'s `CANONICAL_FIELDS` covers every substantive field written to the event (`membershipId`, `uid`, `tenantId`, `changeType`, `fromValue`, `toValue`, `changedBy`, `changedAt`) — the only excluded fields are `contentHash` itself (circular) and the server-assigned `createdAt`/`batchId`, which mirror `hashAnchor.js`'s own documented exclusions for DTCs (values that are added post-creation or mutate over time, not authored content). Tampering with any hashed field after the fact would be detectable once anchoring ships; no gap found here.

## The gap, confirmed rather than assumed

A targeted check found: **`memberships.status` (who has access) is mutated in place today**, with only an `updatedAt` timestamp — no record of what it changed from, when, or who triggered it. There is no endpoint anywhere that changes a member's `role` after creation either — role grants happen today via direct Firestore writes or admin scripts, entirely outside any application-level audit trail. This matters more than an ordinary bug because it's the layer everything else — including the consent model below, and every tenant-scoping fix made earlier this session — depends on being trustworthy. If a permission grant can be silently rewritten with no trace, so can a fake consent approval.

**Firestore security rules cannot close this bypass — verified, not assumed.** `memberships` already has `allow write: if false` for client SDK, so the client-side path was never the exposure. Admin SDK access bypasses Firestore rules on every Firebase project, by design — no rule change closes that. **Checked: Firestore Data Access audit logging is not currently enabled for this project.** That log stream would independently record every Admin SDK read/write to `memberships` (or any collection) with the identity that performed it — but per round 2's red-team pass, this needs a real scope/cost decision before enabling, not a blanket flip. See Open Decisions and Build Status.

## The right fix reuses infrastructure that already exists

DTCs already get exactly this treatment: a SHA-256 `contentHash` computed at creation (`services/anchor/hashAnchor.js`, CODEX 50.14 Layer A), batched daily into a Merkle tree and anchored to Bitcoin via OpenTimestamps (`services/anchor/dailyBatchAnchor.js`, CODEX 50.14 Layer B — `dtcAnchorBatches/{YYYY-MM-DD}`, gathering DTCs with `batchId == null`). This is not "every write is its own blockchain transaction" — it's hash-and-batch, already running, already cheap. The fix is to widen what feeds an *anchor pipeline*, not invent a new one.

**Design decision: a separate, parallel batch job, not a modification to `dailyBatchAnchor.js` itself.** The existing DTC anchoring pipeline is live production infrastructure for real, already-anchored records — extending it in place risks a mistake touching DTC anchoring itself. A sibling job (same Merkle/OTS primitives, its own batch collection) gets the same tamper-evidence without touching what already works.

## What needs to become append-only + anchored

1. **Membership/role/status changes** — `membershipEvents`: `{ membershipId, uid, tenantId, changeType, fromValue, toValue, changedBy, changedAt, contentHash }`, same shape as `logbookEntries` relative to `dtcs`. The `memberships` doc stays the fast-lookup current state; the event log becomes the actual source of truth.
2. **Sign-up/account-creation events** — already timestamped, not yet hash-anchored. Same treatment, same reason.
3. **Actual access events** (who *viewed* a sensitive record, distinct from who's *permitted* to) — does not appear to exist at the application level at all today. Matters most for FERPA-type contexts, where "who accessed this record" is often its own explicit requirement, separate from authorization. Largest lift of the three — needs instrumentation across every sensitive read route, not just the mutation sites.

## Relationship to CODEX 97's cross-tenant consent model

Moved here from CODEX 97 in full, since it's the same underlying capability (a trustworthy identity/access layer), not a worker-comms topic:

**The rule:** a person's own data may unify across tenants/institutions *only* when the person has explicitly authorized that specific relationship — never silently, never by default, never inferred from an old, differently-scoped authorization.

1. **Deny by default, always.** No response to an access request means denied, not approved — fail-safe, not fail-open. This is the actual fix already shipped for `pilotCurrency.js` (Dispatch checking a crew member, and self-view) and `clinicalEvaluation.js`'s third-party view: scope to the current/requesting tenant only until a real consent mechanism exists.
2. **No timeout ever converts to approval — named explicitly, per the red-team pass.** A pending request that sits unanswered (person hasn't logged in, missed the notification) stays pending, never auto-approved. This must never be "optimized" later for user friction — an auto-approve-on-timeout would silently break the one invariant this whole model is built around. **Decided, per round 2, not left conditional:** a request unanswered for 7 days expires to **denied** and is removed from the pending queue — the requester must resubmit if still needed. Never approved by default, and never left in indefinite limbo either.
3. **Consent is scoped narrowly: (person, data type, granting tenant/relationship, purpose) — never a blanket toggle.** This is what makes a student-later-becomes-employee scenario self-enforcing: "share my nursing records with Clearwater Nursing's instructors, for coursework evaluation" does not match a later request from an unrelated employer — no matching key, no access, forced to ask fresh.
4. **`purpose` is a fixed, enumerated set, matched exactly — never free text, substring, or category matching.** Per the red-team pass: if purpose were loosely matched, a requester could phrase a new request just close enough to an old approved one to slip through. The enum is defined and versioned by SOCIII (not per-tenant free-form), and a request with a purpose outside the enum is rejected outright, not fuzzy-matched to the nearest one.
5. **The nightmare scenario this has to survive:** a compromised or malicious institution masking an access request as routine, hoping the person waves it through without noticing. The mitigating design: **deny the requesting party, notify the actual person through a channel the requester cannot control or intercept, and require their explicit approval before anything is granted.** The notification must go through the person's own authenticated SOCIII session (already logged in, ideally MFA-backed) as the primary channel — email/SMS is a fallback notice only, never the approval mechanism itself, or a phished/intercepted link defeats the whole safeguard.
6. **The approval prompt must be transparent by design:** who is asking, what specifically they want, and why (if given).
7. **On approval, the person chooses "ask me every time" or "don't ask again for this exact relationship + purpose."** Either way, every actual access is logged permanently — silence applies to the notification, never to the record. (This is exactly the append-only access-event log described above — the consent model's audit trail *is* this doc's access-event log, same primitive.)
8. **Anomaly detection as a backstop — specified, not a bullet point, per the red-team pass.** Trigger: more than 5 new cross-tenant access requests from the same requesting tenant within a rolling 24-hour window (tune with real data once this exists; the point is a concrete number exists, not that this exact one is final). Response: auto-suspend that tenant's ability to issue new cross-tenant requests pending review (same kill-switch pattern used elsewhere in this session, not a new mechanism), **and** an immediate real-time alert. **Per round 2's red-team pass:**
   - **False-positive path, decided:** the suspended tenant gets a generic notice that its cross-tenant request ability is paused pending review (never *why*, to avoid tipping off an actual bad actor probing for access) plus a defined **4-business-hour** review SLA — a legitimate burst (e.g. an employer onboarding many former students at once) becomes bounded friction, not silent indefinite lockout.
   - **Alert channel, with a distinguishability requirement:** routed through the same channel CODEX 97 built for external-facing actions (SMS/Telegram via `comms.send_sms_v1`/`comms.send_telegram_v1`), not a second, separately-invented notification system — but a security/anomaly alert must carry a distinct, visible marker (e.g. a `[SECURITY]` prefix) and is never batched or summarized the way a routine "email sent"/"post published" nudge can be. Reusing the pipe is fine; looking identical to routine traffic in it is not, given this is the alert that can least afford to get lost.
   - Owner: Sean, until this is a large enough surface to delegate.
9. **Scope, precisely:** applies only when the requesting tenant does *not* already have an established relationship with the person. Does not apply to an instructor/dispatcher already legitimately enrolled-with that person on their current tenant — that's the ordinary membership+role check (already fixed on `nurse-edu:students`), not a new-relationship consent event.

**Not yet built** — real, standalone feature (consent-record data model, notification/approval flow through an authenticated channel, anomaly detection). What's live today is the safe interim default (deny/scope-to-current-tenant) on the flagged functions, not the consent flow itself.
